# 대용량 텍스트/CSV 에디터 리서치

- 날짜: 2026-07-22
- 목적: 10GB+ CSV/TSV/텍스트를 즉시 열어 테이블로 보는 빠른 뷰어/에디터를 만들기 전, "바로 쓸 것 vs 만들 때 재사용할 것" 정리
- 방법: deep-research (106 에이전트, 6개 검색 각도, 소스 23개 → 주장 114개 → 상위 25개 적대적 검증, 3표 중 2표 기각제). 검증 통과 22 / 기각 3.

---

## 결론 (TL;DR)

- **10GB+ 즉시 열기 + CSV 테이블 분리를 GUI로 둘 다 잘하는 오픈소스는 없다.** → 이 프로젝트를 만들 이유.
  - klogg = 10GB+ 즉시 열기 O, CSV 테이블 분리 X (로그 뷰어)
  - csvlens / Tad / VisiData = CSV 테이블 O, 10GB+ GUI 즉시 열기가 X 또는 미입증
- **바퀴를 새로 만들 필요는 없다.** Rust `memmap2 + csv-core` 위에 얹으면 파일 읽기/파싱은 해결. 알맹이(인덱서·가상 스크롤·컬럼 UI·찾기바꾸기)만 만들면 됨.
- **Rust 추천** (C++보다 이 스택이 잘 갖춰짐).
- **AVX512는 목표에서 제외.** 병목은 SIMD 파싱이 아니라 I/O + 렌더링. mmap + lazy 인덱싱 + 가상 스크롤이면 AVX512 없이도 "즉시" 달성 가능. (검증된 AVX512 Rust CSV 파서도 존재하지 않음.)

## ① 바로 쓸 만한 것 (완성 도구)

| 도구 | 언어 | ⭐ | 형태 | 10GB+ | CSV 테이블 | 구분자 | GitHub |
|------|------|-----|------|-------|-----------|--------|--------|
| **klogg** | C++/Qt | ~3.4k | GUI | O (명시 확인) | X | — (로그) | variar/klogg |
| **csvlens** | Rust | ~3.9k | TUI | 미입증 | O | 콤마/탭/파이프 `-d`, 자동감지 | YS-L/csvlens |
| **Tad** | TS/Electron | — | GUI | 미주장 | O | DuckDB 위임 | antonycourtney/tad |
| **VisiData** | Python | — | TUI | X (RAM 한계) | O | 다양 | saulpw/visidata |

- **klogg** — README에 "10+ Gb is not a problem", "디스크에서 직접 읽어 메모리에 안 올림", "멀티스레드 + SIMD(Intel Hyperscan)" 명시. 21억 줄 초과도 지원. **단, 로그 뷰어라 콤마/헤더 파싱 없음.** → 속도 벤치마크 레퍼런스지 대체재는 아님.
- **csvlens** — "less for CSV". 구분자 완벽 지원(`-d <char>`, `-d auto`, `-t`). **하지만 README에 대용량 처리 메커니즘(mmap/인덱싱/스트리밍) 언급이 전혀 없음** → 10GB+ 근거 미확인. GUI 아님(TUI). → CSV UX 레퍼런스.
- **Tad** — DuckDB에 파싱 위임 + SlickGrid 가상 스크롤(수백만 행). 위임 + 가상스크롤 패턴이 참고 가치. 구체적 10GB+ 수치는 주장 안 함.
- **VisiData** — Python 92%, in-RAM이라 10GB+엔 느림. 공식 문서가 10GB 초과 시 polars/DuckDB 권고. Windows는 WSL 필요.

**→ 즉시 쓸 완벽한 정답 없음. klogg=속도 레퍼런스, csvlens=CSV UX 레퍼런스.**

## ② 만들 때 재사용할 것 (Rust 엔진 스택)

| 크레이트 | 역할 | 근거 |
|----------|------|------|
| **memmap2** | mmap I/O (Windows 포함) | 255M+ 다운로드, Windows MSVC 빌드 확인. 10GB를 demand-paging으로 lazy 매핑 |
| **csv-core** (BurntSushi) | no_std, alloc 없는 pull 파서 | mmap 버퍼 슬라이스를 직접 넘겨 필드 lazy 파싱 — 커스텀 뷰어에 이상적 |
| **csv** (BurntSushi) | 고수준 스트리밍 파서 | 레코드 온디맨드 iterator, "메모리에 안 올라가는 파일 처리에 적합" |
| **Polars** | Arrow 컬럼너, 멀티스레드, SIMD, out-of-core | 무거운 옵션. CSV 파싱/집계엔 강력하나 텍스트 에디팅 엔진은 아님 |

- **추천 조합**: `memmap2`(파일 매핑) + `csv-core`(보이는 줄만 lazy 파싱). ripgrep 저자(BurntSushi)의 대용량 노하우 반영. Polars는 정렬/필터 같은 무거운 연산이 필요할 때만.

### 기각/주의 (검증에서 탈락)
- **AVX512 Rust CSV 파서는 없음.** `fastcsv`·`csv_lib` 있으나 AVX2/NEON까지고 채택률 거의 0(별 1개). 아키텍처 참고용이지 의존성으로 신뢰 불가.
- `csv_lib`의 "13GB 처리"(1-2 기각), "멀티코어 병렬"(0-3 기각) 주장 모두 **기각**.
- AVX512가 꼭 필요하면 C++ **simdjson** 계열(런타임 AVX512 디스패치)의 접근을 직접 이식해야 함. → 이번 프로젝트에서는 제외.

## ③ "즉시 열기" 아키텍처 핵심 (검증 완료)

10GB를 즉시 여는 비결 = **파일을 다 안 읽는 것.**

1. **디스크에서 직접/청크 읽기** — 메모리에 통째로 안 올림 (klogg). klogg는 **줄 위치 맵만 압축 저장**(CompressedLineStorage) → RAM 절약, 21억 줄 초과 지원
2. **mmap / demand paging** — 필요한 페이지만 (memmap2)
3. **가상 스크롤** — 보이는 몇십 줄만 렌더링 (Tad/SlickGrid, 수백만 행)
4. **증분 스트리밍 파싱** — 레코드 단위 온디맨드 (csv, Polars)
5. **백그라운드 스레드 비동기 인덱싱** — UI 논블로킹 (klogg의 LogDataWorker)

> **rope 자료구조(xi/helix/zed)는 확정 근거 안 나옴.** rope는 "편집" 최적화라 10GB 뷰 위주엔 단순 **줄 오프셋 인덱스**가 더 적합할 가능성 큼.

## 프로젝트 시사점

- 바로 쓸 완성품 없음 → 만드는 게 맞음. 빈틈 확인됨.
- 만들 알맹이: (a) 백그라운드 줄 오프셋 인덱서, (b) 가상 스크롤 렌더러, (c) 구분자별 컬럼 정렬 UI, (d) 찾기/바꾸기.
- 병목은 I/O + 렌더링. AVX512 불필요.
