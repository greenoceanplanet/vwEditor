# 파싱 오류 행 검출 (Bad Rows)

**작업 범위:** `afeca78..31950e5` (2 커밋)
**날짜:** 2026-07-25

표 모드에서 "전체 규칙과 어긋나는 행"을 찾아 별도 창에 목록으로 보여 준다.
파일을 열면 자동으로 검사하고, 항목을 클릭하면 본문이 그 행으로 이동한다.

---

## 1. 무엇을 오류로 보는가

| 유형 | 판정 | 예 |
|---|---|---|
| `FieldCount` | 필드 수가 기대치와 다름(부족·초과 모두) | 7컬럼 파일의 `a,b,c` |
| `UnbalancedQuote` | 큰따옴표 개수가 홀수 | `a,"b,c` |
| `DecodeError` | 디코딩 결과에 대체문자 U+FFFD | CP949 파일을 UTF-8로 읽을 때 |

기대 컬럼 수는 헤더 필드 수(헤더가 없으면 앞 데이터 행 샘플의 최댓값)이며,
`render_table`이 실제로 그리는 컬럼 수(`table_col_count`)와 **같은 함수**를 쓴다.
따로 계산하면 "화면엔 7칸인데 오류 창은 8을 기대한다"가 된다.

**빈 줄은 오류가 아니다.** 파일 끝 개행이나 구분용 빈 줄이 흔하다.

---

## 2. 검사 순서가 규칙이다

세 검사의 순서는 취향이 아니라 **뒤의 검사가 앞의 실패에 오염되기 때문**이다.

```
입력:  "\u{FFFD},\"b        (대체문자 + 홀수 따옴표 + 필드 수 불일치)
```

- 디코딩이 깨진 줄은 구분자 바이트가 대체문자로 바뀌어 **필드 수가 엉뚱하게** 나온다
- 따옴표가 안 닫힌 줄은 `split_fields`가 남은 전부를 한 필드로 삼아 **역시 필드 수가 어긋난다**

그래서 순서는 **디코드 → 따옴표 → 필드 수**다. 뒤집으면 사용자가 진짜 원인
(인코딩이 틀렸다) 대신 증상(필드가 3개다)을 좇는다.

이 순서를 지키는지 테스트가 직접 본다 — 세 문제를 **한 줄에 동시에** 담아
가장 근본 원인이 보고되는지 확인한다. 순서를 바꾸면 변이 테스트에서 4건이
실패한다.

---

## 3. 스캔 진입점이 둘인 이유

계획서에는 mmap 스캔 하나뿐이었다. 실제로는 둘이 필요했다.

**편집 모드에서는 파일 바이트가 더 이상 진실이 아니다.** 셀을 고치거나 구분자를
변환한 뒤에도 mmap을 훑으면 디스크에 남은 옛 내용을 검사하게 되어,

- 방금 고친 행이 계속 오류로 남고
- 방금 망가뜨린 행은 잡히지 않는다

```rust
pub fn scan_errors(source, index, enc, ...)  // 뷰 모드 — mmap, 백그라운드 스레드
pub fn scan_lines(lines: &[String], ...)     // 편집 모드 — 인메모리, 동기
```

편집 모드가 동기인 이유: 줄이 이미 `String`으로 디코딩돼 있어 훨씬 싸다
(디코딩도 mmap 접근도 없다).

두 경로가 **같은 답**을 내는지는 테스트가 대조한다(`mmap_and_lines_paths_agree`).
한쪽만 고치면 편집 모드에 들어갔다 나올 때 목록이 달라진다.

## 4. 상한 — 자르되 숨기지 않는다

구분자를 잘못 고르면 **모든 행**이 오류가 된다. 1,500만 행이면 `RowError`
1,500만 개(수 GB)이고, 사람이 볼 수 있는 양도 아니다. 그래서 `MAX_ROW_ERRORS
= 10,000`.

문제는 자르는 방식이었다.

**버린 개수를 반드시 센다.** 상한만 두고 조용히 자르면 "오류 10,000개"가
화면에 뜨는데 실제로는 300만 개일 수 있다. 사용자가 목록을 다 훑고 **"다
고쳤다"고 믿게 되는 것이 가장 나쁜 결과**다. 그래서 `ScanResult`가
`errors`와 `dropped`를 함께 들고, 상태바와 창이 둘 다 "일부만 보여 준다"를
명시한다.

**어떤 것을 남길지도 결정적이어야 한다.** 처음엔 "먼저 도착한 것 우선"이었는데,
rayon의 병합 순서는 API가 보장하지 않는다. 도착 순서에 기대면 같은 파일을 두 번
열어도 목록이 달라질 수 있고, 무엇보다 사용자가 원하는 것은 "파일 앞쪽부터
고쳐 나가는 것"이지 "스레드가 먼저 끝낸 조각"이 아니다. 그래서 **행번호가 작은
쪽**을 남긴다.

## 5. 걸린 것 (1) — 테스트가 검증하지 못하는 정렬

병합 결과를 오름차순으로 유지하려고 `sort_unstable_by_key`를 넣어 뒀는데,
변이 테스트에서 **그 정렬을 통째로 지워도 0건 실패**했다.

원인: rayon이 indexed 병렬 이터레이터를 **왼쪽부터 순서대로** 접어 주고,
청크 안에서도 행을 오름차순으로 훑는다. 그래서 정렬이 없어도 결과가 이미
오름차순이었다 — 정렬은 실행되지만 아무 일도 하지 않는 죽은 코드였다.

"테스트가 못 잡으니 테스트를 더 쓰자"가 아니라, **그 순서를 rayon에 기대는 것
자체가 문제**였다. 보장되지 않은 성질에 기대면서 그 사실이 코드 어디에도
안 적혀 있었다.

고친 방법 — 정렬이 아니라 **병합**으로 바꿨다:

```rust
/// **전제:** a와 b는 각각 행번호 오름차순이다(청크가 행을 오름차순으로
/// 훑고, 이 함수가 그 성질을 보존한다 — 귀납).
fn merge_results(a: ScanResult, b: ScanResult, limit: usize) -> ScanResult
```

이제 상한 적용(작은 행번호 우선)과 순서 유지가 **한 연산**이라 둘 다 진짜로
일한다. 그리고 `merge_results`를 **직접** 부르는 테스트를 따로 뒀다 —
`scan_lines` 너머로만 보면 "큰 행번호가 먼저 온" 상황이 아예 만들어지지
않아서, 병합 규칙을 지워도 테스트가 통과한다.

> 이 코드베이스에서 반복되는 결함의 변종이다. 지난번(구분자 변환)은 테스트가
> 판정식을 **복사**해서 못 잡았고, 이번엔 테스트가 그 코드 경로를 **구성하지
> 못해서** 못 잡았다. 둘 다 "통과한다 = 검증됐다"가 아니었다.

## 6. 걸린 것 (2) — 변이 테스트가 실제 성능 결함을 찾았다

무효화 설계에서 이런 변이를 걸었다: **편집 경로에서 개정 번호 기록을 생략**.

```rust
doc.row_errors_revision = doc_revision(doc);   // ← 이 줄을 지우면?
```

처음엔 0건 실패였다. 지워도 테스트가 다 통과했다.

이유를 따져 보니 결함이 있었다. 이 줄이 없으면 `row_errors_revision`은 0에
머무는데 `doc_revision`은 편집마다 커지므로, **신선도 판정이 항상 "낡음"** 이
된다. 그러면 편집 모드인 동안 **매 프레임(초당 수십 번) 전 행을 다시 훑는다.**
1,500만 행이면 앱이 멈춘 것처럼 보인다.

기존 테스트가 못 잡은 이유: 뷰 모드로만 확인했는데, 뷰 모드는 편집 버퍼가
없어 개정 번호가 늘 0이라 **우연히 맞는다**. 편집 모드에서 개정 번호를 0이
아니게 만든 뒤 확인하는 테스트를 추가하니 잡혔다.

## 7. 무효화 — 지점마다 걸지 않고 관측한다

오류 목록은 "이 시점의 데이터"를 설명하는 캐시다. 데이터가 바뀌면 버려야 한다.

편집을 수행하는 자리가 `app.rs`에 **열 곳이 넘는다.** 지점마다 손으로
무효화를 걸면 나중에 추가되는 편집 하나가 조용히 빠지고, 그때 증상은
"오류 목록이 가끔 안 맞는다"라 추적하기 가장 나쁜 종류다.

그래서 `UndoStack`에 개정 번호를 두었다. 모든 편집이 예외 없이 `push`를
지나고, 되돌리기는 `undo`를 지나므로 **두 곳에서만** 세면 전부 잡힌다.

```rust
pub fn revision(&self) -> u64
```

`dirty`나 스택 길이를 쓰지 않은 이유:

- `dirty`는 한 번 서면 계속 서 있어 "그 뒤로 **또** 바뀌었는가"를 답하지 못한다
- 스택 길이는 상한(`UNDO_LIMIT`·바이트 예산)에 걸리면 push를 해도 그대로거나
  줄어들 수 있어 편집을 놓친다

파싱 **기준**이 바뀌는 경우(구분자·인코딩·헤더)는 데이터가 그대로라 개정
번호가 안 움직이므로, 그 지점들은 명시적으로 `invalidate_error_scan`을 부른다.

## 8. 스크롤 — 계획서를 따르지 않은 곳

계획서는 `TableBuilder::scroll_to_row`를 쓰라고 했지만, 그건 이 코드베이스가
**이미 기각한** 방법이다([app.rs:1736](../src/app.rs#L1736) 주석) — egui 0.28.1이
그 요청을 0.1~0.3초 애니메이션으로 감는다.

대신 거터 클릭과 **같은** `gutter_click_target`을 쓴다. 논리 행 → 화면 행
변환에는 정렬 permutation 역매핑이 필요한데, 그 로직을 두 벌 두면 한쪽만
고쳐져 어긋난다.

## 배운 것

**"테스트가 통과한다"와 "검증됐다"는 다르고, 어긋나는 방식이 여러 가지다.**
지난 작업에서는 테스트가 판정식을 복사해서 못 잡았다. 이번에는 두 가지가 더
나왔다 — 테스트가 그 코드 경로를 **구성하지 못하는** 경우(정렬), 그리고 다른
모드로 검사해서 **우연히 맞는** 경우(개정 번호). 셋 다 "이 테스트가 이 변이를
잡는가"를 물어야만 드러난다.

**죽은 코드는 "지워도 되는 코드"가 아니라 "잘못된 가정의 흔적"일 수 있다.**
정렬이 아무 일도 안 한 이유는 rayon의 병합 순서가 우연히 맞아떨어져서였다.
지우고 끝냈다면 보장되지 않은 성질에 계속 기댔을 것이다.

**상한은 "얼마나 자를까"보다 "잘랐다는 걸 어떻게 알릴까"가 어렵다.** 목록만
보고 다 고쳤다고 믿는 것이 오류를 못 찾는 것보다 나쁘다.

**무효화는 규율이 아니라 구조로 막아야 한다.** 편집 지점 열 곳에 "여기서도
무효화를 부르자"는 규율은 열한 번째 지점에서 깨진다. 모든 편집이 지나는
길목에서 한 번 세면 안 깨진다.
