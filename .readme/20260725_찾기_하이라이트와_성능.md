## 요약

찾기에 하이라이트를 붙이는 작업으로 시작했는데, **성능 문제가 연달아 드러나
그걸 잡는 게 작업의 대부분**이 됐다. 사용자가 실사용 파일(1,542만 행 TSV)에서
"먹통이 된다"고 세 번 보고했고, 세 번 다 원인이 달랐다.

최종 결과: 실사용 파일의 컬럼 완전일치 추출이 **229초 → 0.27초 (845배)**.

## 1. 만든 기능

### 전체 매치 하이라이트

- 검색어가 있는 모든 곳에 **옅은 보라** 음영, 현재 매치(Find Next 대상)는 **진한 보라**
- 화면에 보이는 행만 매 프레임 계산한다(가상 스크롤이라 수십 개뿐 — 값싸다)
- 뷰 전용 셀도 검색 중이면 galley 경로로 그린다. 검색어가 없으면 기존 `Label`
  경로 그대로 — 검색 안 할 때는 픽셀 단위로 이전과 같게 해서 회귀를 막았다

### 스크롤 마커 거터

데이터 영역 오른쪽 14px 세로 띠에 **문서 전체**의 매치 분포를 보라 눈금으로.
클릭하면 그 위치로 점프.

`Table::body`가 `ScrollAreaOutput`을 삼켜(`()` 반환) egui 기본 스크롤바 위에
겹쳐 그릴 수 없다. 그래서 별도 `SidePanel`로 직접 그린다.

행이 수백만이어도 **거터 높이 픽셀 수만큼만** 그린다(같은 정수 y는 한 번만).
매치가 없으면 거터 자체를 안 그려 데이터 폭을 아낀다.

### 매치 옵션 3지

`Partial` / `Whole word` / `Whole cell` 라디오(배타). Whole cell은 표 모드에서만 활성.

`FindOptions { match_case: bool, scope: MatchScope }`로 재구성했다.
Whole cell 판정은 `find_in_line_scoped(hay, needle, opts, delim)`이 하고,
셀 경계는 `parse::field_slice`(따옴표 처리가 이미 올바르다)를 재사용한다.

### 찾기/바꾸기 별도 창

하단 바가 좁아 불편하다는 요청으로 `egui::Window`로 옮겼다. 입력란 260px,
세로 레이아웃, 매치 행 수 표시. `Ctrl+F` / `F3` / `Enter` / `Escape` 유지.

### Page Up / Down

페이지 단위 스크롤. 한 행 겹쳐 문맥이 이어진다. 표·텍스트 모드 둘 다.
찾기 입력란에 타이핑 중이거나 셀 편집 중이면 문서로 새지 않는다.

## 2. 성능 — 세 번의 오진과 최종 원인

이 절이 이 작업의 핵심이다. **매번 측정 없이 추측해서 틀렸고, 측정하고 나서야
맞췄다.**

### 1차 보고: "입력만 하면 먹통"

**원인**: 하이라이트를 라이브 검색어(`find_query`)에 묶어 놨다. 그래서 한 글자
칠 때마다 `needs_rescan`이 변경을 감지해 문서 전체를 자동 스캔했다.

**해결**: 하이라이트를 **명시적 스냅샷**으로 바꿨다.

```rust
pub struct Highlight { query: String, opts: FindOptions, rows: Vec<u32> }
pub highlight: Option<Highlight>,   // Document에
```

- `Find All` 버튼을 눌렀을 때만 스캔하고 스냅샷을 만든다
- 렌더는 `doc.highlight`만 본다 — 라이브 `find_query`를 안 본다. **그래서 타이핑해도
  스캔이 0번**이다
- Find Next/Prev는 `highlight`를 안 건드린다(현재 매치만 이동)
- 검색어를 고쳐도 이전 하이라이트는 다음 Find All까지 유지(사용자 확정)
- 추출도 새 탭에 `highlight`를 채워 보낸다 = "추출 = 새 탭에 Find All 한 셈"

자동 스캔(`needs_rescan`/`refresh_match_scan`/`match_query`)은 통째로 제거했다.
이제 `scan_all_matches`를 부르는 곳은 **Find All과 추출 둘뿐**이다.

### 2차 보고: "1500만 행 컬럼 완전일치가 1분 넘게 응답 없음"

사용자: *"문자열로 읽지 말고 바이트 단위로 일치시키면 안돼?"* — 정확한 지적이었다.

**측정**(2GB / 2200만 행, 흔한 셀값):

| | 이전 | 바이트 |
|---|---|---|
| Whole cell | 335,000 ms | 330 ms (**1016배**) |
| Partial | 34,000 ms | 388 ms |

**원인**: memmem으로 후보 행을 빠르게 찾은 뒤, **후보 행마다** 다시 문자열로
디코딩하고 `split_fields`(모든 필드를 `String`으로 할당) + `chars().count()`를
돌렸다. 흔한 검색어면 그게 2200만 번.

**통찰**: `match_case`면 문자열이 필요 없다.
- **Partial**: memmem 히트 자체가 매치의 증명 — 재판정 불필요
- **Whole cell**: "셀 == 검색어"는 파일 바이트에
  `<구분자|줄시작><검색어 바이트><구분자|줄끝>`로 나타난다. 앞뒤 바이트만 보면 된다

`classify_cell_hit(...) -> CellHit { Confirmed, NeedsRefine, NotCellBoundary }`
순수 함수로 뽑았다. 애매하면(따옴표 개입, 검색어에 구분자 포함) 폴백.

**UTF-16은 폴백**한다. 구분자·개행이 2바이트 코드유닛이라 바이트 경계 판정이
코드유닛 중간에 걸릴 수 있다. CP949는 안전하다 — 트레일 바이트가 전부 ≥0x41이고
리드 바이트가 ≥0x81이라 ASCII 구분자와 겹치지 않는다(리뷰가 한글 블록 전수 확인).

### 3차 보고: "속도 변화 없는데?"

**원인**: `FindOptions::default()`가 `match_case: false`인데, 나는 `match_case: true`
경로만 최적화하고 **벤치마크도 그것만 쟀다**. 사용자는 체크박스를 켜지 않으므로
항상 최적화 안 된 ignore_case 경로를 탔다.

측정: ignore_case Whole cell **412초**, Partial 54초.

이전에 "ignore_case는 바이트로 하면 위음성"이라고 판단했던 건 **needle 한쪽만**
접을 때 얘기였다. **haystack과 needle을 둘 다** ASCII 소문자로 접으면 정확하다.
→ 145배 개선.

### 4차 보고: "extract rows는 하나도 안 빨라졌어"

여기서 **사용자가 실제 파일을 알려준 게 결정적**이었다.

`(대용량 실파일)` — 1,542만 행, 899MB, TSV, **따옴표 0개**,
3번째 컬럼 `인도네시아` 추출 = 12,047행.

내 서브에이전트는 "따옴표 행이 폴백을 타서 느리다"고 진단했는데, **그 파일엔
따옴표가 하나도 없었다**. 파일을 직접 확인해서 알았다.

**진짜 원인**: `bytefast_ci_ok`의 `query.is_ascii()`.

```rust
!query.is_empty() && query.is_ascii() && is_single_byte_enc(enc)
```

`인도네시아`가 비ASCII라 빠른 경로에서 배제 → 1,542만 행 전부 디코딩.

"유니코드 대소문자 접기는 바이트로 안전하지 않다"는 판단 자체는 맞지만
**과하게 넓게 막았다**. 유니코드 전수 프로브로 확인:

- 비ASCII 중 `to_lowercase()`로 바뀌는 문자: **1,462개** (À, É, İ, Σ …)
- **한글 음절 11,172자 중 바뀌는 것: 0개** — 한글엔 대소문자가 없다

**결과: 229.33초 → 0.27초 (845배)**, 12,047행 정확히 일치.

### 곁다리로 잡은 것

`parse::split_fields`가 호출마다 `csv_core::ReaderBuilder::build()`로 NFA/DFA
전이 테이블을 새로 만들고 있었다 — **호출당 14.6µs**. 74.9만 호출 = 10.9초.

`thread_local`로 `Reader`를 캐시하고 delim이 바뀔 때만 재빌드, 아니면 `reset()`.
**10.90초 → 0.41초 (26.7배)**. 표 셀 렌더링·정렬·`table_col_count`도 같이 빨라졌다.

> `reset()`이 load-bearing인 이유: csv_core가 선두 BOM(U+FEFF)을 **첫 호출에만**
> 벗긴다. 안 부르면 BOM 파일의 첫 필드가 깨진다. rayon 워커에서도 부르는데
> `thread_local`이라 각 워커가 자기 Reader를 갖는다(Mutex 불필요).

### Page Up/Down이 느린 것

egui 0.28.1에는 `ScrollAnimation`/`style.scroll_animation`이 **없다**(레지스트리
소스 확인). `TableBuilder::vertical_scroll_offset`으로 행높이 × 행번호를 직접
지정해 1프레임 즉시 점프하게 했다. 스크롤 요청을 소비한 프레임에만 적용하므로
휠·드래그는 그대로다.

## 3. 정확성을 지킨 방법

바이트 최적화는 **결과를 바꾸면 안 된다**. 절대 계약을 하나 세웠다:

> `scan_all_matches`의 결과는 항상 `find::matching_lines` 브루트포스와
> **정확히 같은 행 집합**이어야 한다.

규율:
- 빠른 경로는 **"확실히 매치"** 또는 **"폴백 필요"**만 판단한다
- **"확실히 비매치"를 바이트만으로 단정하지 않는다**
- 위양성은 안전하다(최종 판정이 걸러낸다). **위음성만 치명적**이다
- `find.rs`는 정확성 오라클로 남겨 두고 최적화 과정에서 손대지 않았다

### 리뷰가 잡은 결함들

이 계약이 없었으면 전부 조용히 지나갔을 것들:

**따옴표 셀 위음성 (Critical)** — `"a"a`는 화면에 `aa`로 보이지만 파일 바이트에는
`aa`가 인접해 없다. "히트 0개 = 비매치"로 단정해 **매치되는 행을 잃었다**.
랜덤 퍼징 79.7만 건이 못 잡은 걸 따옴표 알파벳 전수 프로브가 잡았다.
`"` 없는 행만 비매치로 단정하도록 고쳤다.

**`İ` 다다자 확장 위음성 (Critical)** — U+0130은 소문자화하면 **두 글자**
(`i` + U+0307)로 확장되는데, 그 둘이 각각은 판정을 통과해서 needle `i̇`가 빠른
경로를 타고 행을 놓쳤다. 구현자의 전수 테스트가 "소문자가 정확히 1글자"인
경우만 모아서 이 구멍에 눈이 멀어 있었다. 다다자 확장의 조각을 전수 스캔하니
정확히 `{i, U+0307}`뿐 — 증명 가능한 완전한 규칙으로 막고, **그 전수 스캔
자체를 테스트로 고정**했다.

**내 브리프의 판정식 오류** — `to_lowercase(c) == c`만 보면 needle `é`가 통과하는데
브루트포스는 파일의 `É`를 접어서 매치한다 → 위음성. 구현자가 대칭 판정
(`lo == c && up == c`)으로 고쳤고, 전수 프로브로 내 버전에 **1,453개 구멍**,
대칭 버전 **0개**임을 증명했다.

**인덱싱 중 재스캔 폭주** — 2GB 파일을 검색 상태로 열면 8MB 청크마다(약 256번)
풀 재스캔이 돌아 UI 스레드가 수 분간 먹혔다. `Phase::Complete` 전환 시 1회만
재스캔하게 고쳤다.

**추출 Ctrl+S가 매번 파일 선택창** — 추출 탭은 경로가 비어 파일 선택창으로
폴백하는데, 저장 성공 후 `doc.path`를 갱신하지 않아 저장할 때마다 경로를 다시
입력해야 했다.

리뷰는 검증에 **336,000건**(Task G), **797,000건**(Task H) 랜덤 차등 비교를 돌렸고,
CP949 트레일 바이트 안전성은 한글 블록 전수로 증명했다.

## 4. 이번에 배운 것

### 측정하지 않으면 매번 틀린다

같은 증상을 네 번 보고받았고 원인이 네 번 다 달랐다. 그때마다 코드를 읽고
"여기가 병목이겠다"고 판단했는데 **세 번 틀렸다**. 맞춘 건 전부 실제 파일로
측정한 뒤였다.

특히 **벤치마크의 조건이 사용자의 조건과 다르면 의미가 없다**. `match_case: true`로만
재고 "1016배 빨라졌다"고 보고했는데, 사용자는 기본값(`false`)이라 아무 개선도
체감하지 못했다.

### 사용자의 실제 데이터가 최고의 진단 도구다

4차 보고 때 사용자가 파일 경로를 알려준 덕에 즉시 풀렸다. 서브에이전트의
합성 데이터 진단("따옴표 5% 섞인 파일에서 10초")은 그럴듯했지만 **그 파일엔
따옴표가 0개**였다. 실제 파일을 3분 확인한 게 진단 2시간보다 나았다.

### 안전 조건을 넓게 잡으면 기능이 죽는다

"유니코드 접기는 위험하니 ASCII만"이 정확성 면에선 안전했지만, **한국어 사용자의
모든 검색이 느린 경로**를 타게 만들었다. 위험의 범위를 정확히 재면(한글은
대소문자가 없다) 안전하면서도 빠를 수 있었다.

### 랜덤 퍼징은 구조적 구멍을 못 잡는다

79.7만 건 랜덤 비교가 통과한 코드에서, 따옴표 알파벳(`a A " ,`) **전수** 프로브가
즉시 위음성을 찾았다. 랜덤 생성기가 만들던 것은 균형 잡힌 `"…"` 뿐이라
`"a"a` 같은 모양을 합성하지 못했다. **작은 알파벳 전수 > 큰 랜덤**.

## 5. 현재 상태

- `cargo test`: **451 passed / 0 failed / 4 ignored**
- `cargo clippy --all-targets`: 새 경고 0
- `src/app.rs` 11,659줄, `src/find.rs` 970줄 (전체 16,992줄)

### 알려진 한계

- **U+212A KELVIN SIGN** — 유니코드에서 비ASCII가 ASCII로 접히는 **유일한** 경우라,
  검색어 `k`가 `K`(U+212A)가 든 행을 놓친다. 막으려면 `k`/`K` 들어간 검색어가
  전부 느린 경로가 되어 그대로 뒀다(선재 결함, 문서화됨)
- **UTF-16 Whole cell**과 **CP949 match_case Partial**은 후보 행을 디코딩한다
  (바이트 경계가 안전하지 않아 불가피)
- **따옴표 많은 CSV**는 Whole cell 빠른 경로 이득이 줄어든다. 바이트 레벨로
  `split_fields`를 재구현하면 되지만 진실 소스가 둘이 되므로 별도 태스크
- **뷰 모드 찾기는 인덱서가 도달한 행까지만** 훑는다(10GB 부분 인덱싱 시)
- **Page Down을 꾹 누르면** 한 페이지보다 덜 넘어간다 — 화면 위치 관측이
  1프레임 늦다. 단발은 정확. `Table::body`가 스크롤 offset을 안 돌려주는 구조적 제약
- 하이라이트 스냅샷은 편집/정렬 후 행 번호가 어긋날 수 있다(다음 Find All까지
