## 1. "실패"가 없던 감지에 실패를 만들기

기존 `detect_encoding`은 BOM → UTF-8 → **CP949 폴백**이다. CP949 폴백은 어떤
바이트열이든 받아들이므로 **감지가 실패하는 경우가 없었다**. 그래서 SQLite
헤더가 깨진 한글로 보였다.

`detect_text`가 그 앞을 막는다. 순서가 전부다:

1. **BOM은 무조건 텍스트.** UTF-16은 NUL 투성이라 NUL 검사보다 먼저 와야 한다.
2. **NUL이 있으면 바이너리.** 텍스트 파일에는 NUL이 없다.
3. 디코드해서 **대체문자(U+FFFD)가 5% 초과면** 바이너리.

BOM 없는 UTF-16이 2번에 걸리지만 회귀가 아니다 — 기존 감지도 그것을 못 읽었고,
이제는 다이얼로그에서 UTF-16을 **지정해서 열 수 있으니** 오히려 개선이다.

5%는 관대한 값이다. "몇 바이트 깨진 텍스트"(지금도 열리는 파일)는 계속 텍스트로
열고, 무작위 바이트열만 걸러낸다.

## 2. 뷰는 mmap, 편집은 승격 — 텍스트 모드와 같은 구조

사용자가 설계를 정했다: *"화면에 뜨는 영역만 보이도록 하면 되겠지? 만약에
거기서 삽입을 하려고 하게 되면, 그 때 전체를 로딩해서 다시 저장하면 어때?"*

그것이 이미 텍스트 모드가 쓰는 구조였다(`Document.edit`). 헥스도 같은 모양으로
갔다 — `HexState.edit: Option<HexEditBuffer>`가 `None`이면 mmap 뷰,
편집 조작이 오는 순간 전체를 `Vec<u8>`로 올린다. 512MB 초과면 확인 다이얼로그.

헥스 문서는 **줄 인덱서를 돌리지 않는다**(`indexer: None`). 줄 개념이 없기
때문인데, 이 불변식이 뒤에서 두 번 물었다:

- 상태줄이 `LineIndex`의 phase를 읽어 영원히 "Indexing… 0%"를 표시할 뻔했다
  (Task 9에서 헥스 분기로 해결)
- Page Up/Down이 `doc.index.line_count()`(헥스는 영원히 0)를 보고 스크롤을
  포기했다 — **캐럿만 움직이고 화면은 가만히 있었다**. 최종 리뷰가 잡았다.

## 3. 화면 정렬 — 이 세션의 가장 값진 교훈

사용자가 실제로 열어 보고 세 가지를 지적했다:

1. 특정 줌에서 16진수 오른쪽 끝이 잘림
2. 왼쪽 일련번호와 16진수 줄이 가지런하지 않음
3. **오른쪽으로 갈수록 캐럿이 밀려 다른 글자 위에 있음**(헥스·ASCII 양쪽)

셋이 한 뿌리였다. 렌더가 컬럼 폭·캐럿 위치·클릭 역산을 전부
`glyph_width('0') × 문자수`로 **추정**했다. 그 값은 폰트가 알려주는 이상적
폭(실수)이고, 실제 글리프는 픽셀 격자에 반올림돼 배치된다. 차이가 바이트마다
쌓여 32번째에서는 글자 하나 이상 벌어진다. 줌 배율에 따라 반올림 방향이 달라져
**어떤 배율에서만** 드러나기까지 했다.

해법은 추정을 그만두는 것이다. **갤리는 자기가 어디에 무엇을 그렸는지 정확히
안다.**

- 캐럿 위치: `Galley::pos_from_cursor`로 문자 x를 직접 묻는다
- 클릭 역산: `Galley::cursor_from_pos`로 되묻는다 — 그리는 좌표와 읽는 좌표가
  같은 출처라 어긋날 수 없다
- 컬럼 폭: 대표 문자열(`"FF "` × 32)을 실제로 배치해 잰다
- 세로 정렬: 오프셋 칸만 egui `Label`을 써서 그 레이아웃을 탔던 것이 2번의
  원인. 세 칸을 같은 함수로 그리고, 세로 중앙을 **갤리 높이가 아니라 행 높이**
  기준으로 잡는다(갤리 높이는 내용에 따라 달라 칸마다 흔들린다)

**테스트로 못 잡는다는 것을 확인하고 적어 뒀다.** 행 끝 바이트 클릭을 오차 없이
요구하는 회귀 테스트를 넣었지만, 클릭 역산을 옛 나눗셈으로 되돌려도 그 테스트는
통과한다 — 헤드리스 egui의 기본 폰트가 완전한 균등폭이라 두 방식이 같은 답을
낸다. 실제 화면에서만 폰트 힌팅·줌 반올림이 누적된다. 그 한계를 테스트 주석에
명시했다. **시각 정렬은 사람이 화면으로 봐야 하는 종류의 결함이다.**

## 4. 편집 — 니블 상태 기계

헥스 패널은 16진수 **한 자리**(니블) 단위로 입력받는다. `caret: (u64, bool)`의
bool이 "상위 니블인가"다. 규칙 세 가지가 겹치는 자리에서 순서가 중요했다:

- 덮어쓰기 모드: 현재 바이트에 `apply_nibble`, 니블 전진(하위였으면 다음 바이트)
- 삽입 모드(Insert 키): 상위 니블 입력 시 **새 바이트를 끼워 넣고** 하위 니블 대기
- **파일 끝에서는 삽입 모드와 무관하게 삽입** — 덮어쓸 바이트가 없다

세 번째가 두 번째보다 먼저 판정돼야 한다. 리뷰가 이 순서를 추적해 확인했다.

문자 패널은 UTF-8 바이트열로 덮어쓴다 — 한글 한 글자는 3바이트다. 그래서
`HexOp::Overwrite`가 `old`/`new`를 `Vec<u8>`로 들고, **한 글자 입력이 undo
한 번**으로 돌아간다.

## 5. 리뷰가 잡은 것 — 태스크별 리뷰가 볼 수 없던 자리

태스크 9개가 각각 리뷰를 통과했는데, 최종 전체 브랜치 리뷰가 **교차 결함 5건**을
더 찾았다. 태스크별 리뷰가 구조적으로 볼 수 없는 자리들이다:

| 결함 | 왜 태스크 리뷰가 못 봤나 |
|---|---|
| 다중 드롭 시 `pending_binary_open`을 덮어써 파일 유실 | Task 4는 파일 하나만 봤다 |
| 편집이 `last_match`를 무효화하지 않음 — 하이라이트 오위치 + Find Next 깨짐 | Task 6(편집)과 Task 8(찾기)이 각각 리뷰됐다 |
| Page Up/Down이 캐럿만 옮기고 스크롤 안 함 | 렌더(5)·키(6)·기존 페이지 단축키(그 전)의 삼각 지점 |
| `confirm_load` 다이얼로그가 아무것도 잠그지 않음 | Task 6은 다이얼로그를 띄우는 것까지만 봤다 |
| 빈 붙여넣기가 선택을 지우고 캐럿을 갱신 안 함 | 조기 반환이 캐럿 대입을 건너뛰는 한 줄 |

두 번째가 특히 인상적이다. 텍스트 쪽은 편집 시 `last_match`를 지우는 규율이
이미 있었는데(6군데), 헥스는 그 규율을 물려받지 못했다. **같은 문제의 두 번째
구현이 첫 번째의 교훈을 자동으로 받지는 않는다.**

## 6. 변이 테스트가 잡은 두 구멍

13건을 돌려 2건이 살아남았다.

**FFFD 비율 판정 `bad * 20 > total`을 `>=`로 바꿔도 아무 테스트가 안 깨졌다.**
기존 테스트가 3.8%와 37.5%만 밟아 경계가 자유로웠다. 정확히 5%인 표본을
**관측으로 찾아**(encoding_rs가 깨진 쌍을 몇 개의 FFFD로 바꾸는지 가정하지 않고)
그 한 점을 "텍스트"로 고정했다.

**`ensure_hex_edit`이 임계 판정을 무시하고 무조건 로드하게 바꿔도 통과했다.**
512MB짜리 소스를 테스트가 만들 수 없어 확인 대기 경로 전체가 어떤 테스트에도
닿지 않았다. 임계를 상수에서 `HexState.edit_limit` 필드로 옮겨 세 바이트짜리
문서로 "큰 파일"을 재현할 수 있게 했다. **전역 상수나 atomic이 아니라 문서
필드인 이유**는 병렬로 도는 테스트끼리 서로의 임계를 흔들지 않기 위해서다
(atomic으로 먼저 시도했다가 실제로 경합이 났다).

봉합 후 13/13 전부 죽는다.

## 배운 것

1. **위치를 추정하지 말고 그린 것에게 물어라.** `glyph_width × N`은 폰트의
   이상값이고 갤리는 픽셀에 반올림한다. 그리는 코드와 읽는 코드가 다른 출처를
   쓰면 반드시 어긋난다 — 그것도 "특정 줌에서만" 같은 최악의 방식으로.
2. **헤드리스 테스트가 닿지 않는 결함이 있다.** 시각 정렬이 그렇다. 테스트를
   쓰되 그것이 무엇을 못 잡는지 확인하고 주석에 적는 편이, 통과하는 테스트를
   믿는 것보다 정직하다.
3. **태스크별 리뷰는 교차 결함을 구조적으로 못 본다.** 9개가 전부 통과한 뒤
   전체 리뷰가 5건을 더 찾았고, 그중 2건이 Critical이었다. 두 리뷰는 대체재가
   아니다.
4. **같은 문제의 두 번째 구현은 첫 번째의 교훈을 자동으로 받지 않는다.**
   텍스트 찾기는 편집 시 매치를 무효화하는 규율이 있었지만 헥스는 없었다.
5. **변이 테스트는 "테스트할 수 없는 코드"를 드러낸다.** 512MB 게이트가 살아남은
   것은 테스트 게으름이 아니라 설계가 테스트를 막고 있다는 신호였다. 임계를
   주입 가능하게 만든 것이 답이었다.
