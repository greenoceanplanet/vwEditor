# 멀티탭 · 드래그앤드롭 · 찾기/바꾸기 · 행 추출

작성일: 2026-07-24
브랜치: `feat/editing-and-save`
커밋 범위: `e5bf9e5..609182b` (9개)

## 무엇을 만들었나

사용자 요청 네 가지를 순서대로 구현했다.

1. **멀티탭** — 독립적인 문서 여러 개를 탭으로 전환하며 본다
2. **드래그앤드롭** — 탐색기에서 파일을 끌어다 놓으면 열린다. 여러 개면 각각 탭 하나씩
3. **찾기/바꾸기** — 대소문자·단어 단위 옵션, 다음/이전, 하나씩/전부 바꾸기
4. **행 추출** — 검색어가 든 행만 모아 새 탭으로

1번이 나머지의 토대라서 먼저 했다. 2번과 4번은 "새 탭을 만든다"는 점에서 1번에
직접 얹혔고, 3번은 4번의 전제였다.

## 1. 멀티탭

### 구조 변경

```
App.doc: Option<Document>   →   App.docs: Vec<Document> + App.active: usize
```

호출부가 21곳이었는데, 접근자 한 쌍으로 대부분 그대로 살렸다.

```rust
pub fn doc(&self) -> Option<&Document>      { self.docs.get(self.active) }
pub fn doc_mut(&mut self) -> Option<&mut Document> { self.docs.get_mut(self.active) }
```

`.get()`을 쓰므로 `active`가 어떤 이유로든 범위를 벗어나도 패닉이 아니라 `None`이
된다. 다만 `render_table`/`render_text`는 `&mut Document`와 `&mut clipboard_cache`를
**동시에** 필요로 해서, 그 자리만 `self.docs.get_mut(self.active)`로 필드를 직접
쪼개 빌린다. 접근자 메서드를 거치면 `self` 전체가 대여돼서 컴파일이 안 된다.

### 진입점

- `open_path(path, ctx)` — 파일을 열어 **새 탭 추가** 후 활성화. 실패하면 `error`만
  채우고 기존 탭은 그대로 둔다(예전에는 `doc = None`으로 날렸다)
- `add_document(doc)` — 이미 만들어진 `Document`를 새 탭으로. 행 추출이 이걸 쓴다
- `close_tab(idx)` — 닫고 `active` 보정

`File → Open…`이 이제 새 탭이므로, "저장 안 된 변경을 잃는다" 확인이 필요 없어졌다.
`PendingAction::OpenFile`을 통째로 제거했다.

### 탭이 움직이면 인덱스가 어긋난다 (Critical 결함)

리뷰에서 잡힌 가장 심각한 문제다.

`PendingAction::CloseTab(i)`는 **위치 인덱스**를 들고 있는데, "저장 안 된 변경"
확인 창이 **모달이 아니다**. egui 0.28의 `Window`에는 `.modal()`이 없다(0.30에
들어온다). 그래서 확인 창이 떠 있는 동안에도 탭 바가 계속 클릭됐다.

재현:
1. 탭 4개(0~3), 2번과 3번이 dirty. 2번의 ✖ 클릭 → `CloseTab(2)` 대기, 확인 창
2. 깨끗한 0번의 ✖ 클릭 → **확인 없이 즉시 닫힘**. 전체가 왼쪽으로 밀린다
3. "Continue" 클릭 → `close_tab(2)`가 **엉뚱한 (원래 3번) 탭**을 지운다.
   저장 안 된 내용이 조용히 사라지고, 정작 사용자가 확인한 탭은 살아남는다

탭이 3개일 때는 다르게 망가진다 — 인덱스가 범위를 벗어나 "Continue"가 아무 일도
안 한다.

**해결**: 순수 함수 하나로 탭 집합을 얼린다.

```rust
fn tab_bar_locked(&self) -> bool {
    self.pending_action.is_some() || self.show_save_dialog
}
```

탭 바 전체를 `ui.add_enabled_ui(!locked, ...)`로 감쌌다. 같은 가드가 두 가지를
더 고쳤다:

- `pending_action` 덮어쓰기 — 창 X(→`CloseApp` 대기) 후 탭 ✖를 누르면 `CloseTab`이
  덮어써서 앱 닫기가 증발했다
- `save_enc`/`save_bom`이 탭 간에 샌다 — CP949 탭에서 저장 창을 열고 UTF-8 탭으로
  옮긴 뒤 저장하면 **UTF-8 문서가 CP949로 써졌다**

### 그 외

- `edit_dirty()`(활성 탭) vs `any_dirty()`(전체 탭)을 분리. 창 닫기는 후자를 본다
- `tab_label(doc)` 순수 함수 — `●` dirty 표시, 24자 상한, **문자 경계**로 자름
  (바이트로 자르면 한글에서 패닉)
- 탭 바는 탭이 2개 이상일 때만 그린다

## 2. 드래그앤드롭

`ctx.input(|i| i.raw.dropped_files)`를 매 프레임 확인하고, 경로마다 `open_path`를
부른다. 호버 중에는 `Order::Foreground` 레이어에 반투명 오버레이 + `"Drop to open
N files"`를 그린다.

### 병렬성 — 새 스레드를 만들지 않았다

사용자 요청은 "다수를 끌어오면 다수가 동시에 멀티프로세서로 열리는거야"였는데,
**이미 그렇다**. `open_path`가 파일마다 `indexer::spawn_indexer`로 독립된 백그라운드
스레드를 띄우고, 그 인덱서가 내부적으로 rayon으로 병렬 스캔한다. 메인 스레드에서
순차로 도는 건 앞 64KB 감지뿐이고 파일당 수 밀리초다.

그래서 루프만 돌린다. 다음 사람이 "병렬이 아니네?" 하고 스레드를 또 추가하지
않도록 그 판단을 코드 주석으로 남겼다.

### egui API를 소스로 확인했다

이 프로젝트는 egui API를 추측했다가 여러 번 데었다(`Sense::click_and_drag()`의
focusable, `Response::context_menu`가 sense를 union하는 것,
`is_pointer_button_down_on()`이 버튼 무관인 것). 그래서 이번엔 레지스트리 소스를
직접 읽어 확인했다:

- `RawInput::take()`가 `dropped_files`를 `mem::take` 한다 → 매 프레임 비워진다.
  안 그랬으면 같은 드롭이 매 프레임 파일을 다시 열었을 것이다
- `hovered_files`는 clone(비파괴)이고, 드롭 시 egui-winit이 비운다
- `Painter`에는 상호작용 메서드가 아예 없다 → 오버레이가 입력을 못 먹는다.
  `Area`를 썼다면 `.interactable(false)`가 필수였을 것

### 고친 것

- 여러 파일을 드롭했을 때 앞 파일이 실패하고 뒤 파일이 성공하면, `open_path`의
  `error = None` 초기화가 앞선 실패를 지워서 **오류가 아무것도 안 보였다**.
  루프가 마지막 실패를 붙들었다가 복원하게 했다
- 잠금 가드 테스트가 가드를 인라인 복붙해서, 진짜 가드를 지워도 통과했다.
  `plan_dropped_files(dropped, locked) -> DropPlan`으로 뽑아 `update()`와 테스트가
  같은 함수를 쓰게 했다

## 3. 찾기 / 바꾸기

`src/find.rs`를 새로 만들었다. egui를 import하지 않는 순수 모듈이다
(`edit.rs`, `save.rs`, `parse.rs`, `sort.rs`와 같은 그룹).

```rust
pub struct FindOptions { pub match_case: bool, pub whole_word: bool }
pub struct Match { pub line: usize, pub col: usize, pub len: usize }  // col = char 인덱스

pub fn find_in_line(hay, needle, opts) -> Vec<(usize, usize)>;
pub fn replace_in_line(hay, needle, replacement, opts) -> (String, usize);
pub fn find_next(line_count, from, needle, opts, get_line) -> Option<Match>;
pub fn find_prev(...) -> Option<Match>;
pub fn replace_all(lines, needle, replacement, opts) -> (Vec<(usize, String)>, usize);
```

`get_line`을 **클로저로 주입**받는 게 핵심이다. 그래야 `find.rs`가 `Document`를
몰라도 되고, 뷰 모드(mmap+인덱스)와 편집 모드(램 버퍼) 양쪽에서 같은 코드가 돈다.
호출부는 `logical_line(doc, i)`를 넘긴다.

### 대소문자 무시 + 멀티바이트

가장 까다로운 부분. `to_lowercase()`는 **문자 개수가 바뀔 수 있다**(터키어 `İ` →
`i` + U+0307, 2문자). 소문자화한 문자열에서 찾은 인덱스를 원본에 그대로 쓰면
어긋난다.

`folded()` 병렬 배열로 원본 char 인덱스 ↔ 접힌 char 인덱스를 매핑했다. 리뷰가
`İ`(1:2 확장)와 `ẞ`→`ß`를 hay/needle 양쪽 위치에서 검증했다. 부분 확장에 걸친
매치는 `starts_on_boundary`/`ends_on_boundary`로 거부한다 — 계획에 없던 개선이다.

`Match.len`은 **원본에서 소비한 char 수**라서 `chars[col..col+len]`이 항상 원본
텍스트를 그대로 복원한다.

### 그 외 설계

- **빈 needle은 매치 없음** — 모든 위치가 매치가 되면 무한 루프다
- **겹치지 않는 매치** — `"aaaa"`에서 `"aa"`는 2개(0, 2)
- `whole_word`는 `is_alphanumeric() || '_'`로 판정. **한글도 alphanumeric**이므로
  `"가나다"`에서 `"나"`를 단어 단위로 찾으면 매치가 없다. 이게 맞는 동작이다
- `replace_in_line`은 뒤에서 앞으로 치환하는 대신 **복사 커서로 앞에서 뒤로** 새
  문자열을 만든다. 인덱스 시프트 문제가 구조적으로 없다
- 치환문의 `\n`/`\r`는 공백으로 바꾼다. `lines[i]`에 개행이 들어가면 "한 줄 = 한 행"
  불변식이 깨진다 (`edit.rs`의 `sanitize_cell_value`와 같은 이유)
- **Replace All = `EditOp::Replace` 하나**에 바뀐 행 전부. Ctrl+Z 한 번으로 전체 복구
- 바뀐 행만 반환한다. 200만 행에서 10개 바뀌었는데 200만 개를 돌려주면 안 된다

### 계획서가 틀렸던 것 두 가지

구현자가 잡았다.

1. 한글 인덱스 테스트의 기대값이 **산술적으로 불가능**했다. `"가나다ABC가나"`에서
   두 번째 `"가나"`는 char 6, byte 12다(계획서는 5와 9라고 썼다)
2. "`from`은 배타적" 규칙 때문에 **맨 처음 Find Next가 캐럿 위치의 매치를 건너뛰었다**.
   `last_match`가 아직 없을 때만 origin을 하나 물리게 고쳤다. 리뷰가 8개 코퍼스 ×
   모든 origin 위치로 차등 테스트해서 제자리걸음(stall)이 없음을 증명했다

### UI

하단 패널(상태바 위). `Ctrl+F`로 열고 입력란에 포커스, `F3`/`Enter`로 다음,
`Escape`로 닫기. 바꾸기 위젯은 편집 모드에서만 활성(뷰 모드는 버퍼가 없다).

기존 `Ctrl+S`/`Ctrl+Z`/`Ctrl+C/X/V`와 충돌하지 않게, "다른 위젯이 포커스를 쥐면
양보"하는 기존 가드를 따랐다.

### 고친 것

- **뷰 모드 정렬 중에 찾으면 엉뚱한 행으로 스크롤**했다. 정렬된 뷰는 화면 행을
  `permutation[view_row]`로 푸는데, 역방향(논리 → 화면) 매핑이 없었다.
  `logical_to_screen_row`를 추가했다. 정렬된 100만 행에서 매치가 화면 밖으로
  날아가 "Find Next가 아무 일도 안 하는" 것처럼 보였다
- **표 모드에서 행 전체가 선택되지 않았다.** 선택 범위를 `selected_col`(사용자가
  헤더에서 클릭한 컬럼 — 무관한 상태)에서 가져오고 있었다. 실제 컬럼 수를 쓰는
  `table_col_count`를 공유하게 했다
- **치환문이 매치와 같을 때 no-op undo를 push하고 dirty를 세웠다.** `"hit"`을
  `"hit"`으로 바꾸면 버퍼는 그대로인데 "● 변경됨"이 뜨고 저장하라고 물었다.
  누를 때마다 undo 스택이 자랐다. 이 코드베이스가 이미 결함으로 취급하는
  패턴이다(`cut_on_already_empty_cells_pushes_no_undo_step`)

## 4. 찾기 결과 행 추출

찾기 패널의 `Extract Rows` 버튼. 검색어가 든 행만 모아 새 탭으로 연다.
원본은 건드리지 않는다. 0행이면 탭을 안 만든다.

헤더는 **검색 대상에서 빼되 결과 맨 앞에 붙인다**. 헤더에 우연히 검색어가 들어
있다고 추출되면 안 되고, 그렇다고 헤더가 없으면 새 탭에서 컬럼 이름이 안 보인다.

### 인메모리 문서를 어떻게 만들었나

추출 결과는 파일이 아니라 램에만 있는데, `Document`는 `Arc<Source>`(mmap)와
`LineIndex`를 전제로 만들어져 있다. 두 가지 길에서 하나를 골랐다.

**채택**: 추출 결과를 원본 인코딩으로 인코딩(`save::encode_bytes` 재사용)해서
`Source::from_bytes`로 인메모리 Source를 만들고, `LineIndex`를 **동기로** 채운 뒤
`Phase::Complete`로 놓는다. 이미 메모리에 다 있으니 백그라운드 스레드가 필요 없다.

이유: 추출본도 정렬·찾기·편집 모드 진입이 원본과 **똑같이** 되어야 한다.
`Document`가 정상적인 `Source`/`LineIndex`를 가져야 기존 코드가 전부 그대로 돈다.
(대안이던 "곧바로 편집 모드 문서로" 방식은 뷰 모드로 되돌릴 수 없는 반쪽 문서가 된다.)

`Source::from_bytes`는 이미 `#[cfg(test)] from_bytes_for_test`로 존재했다.
정식 공개 함수로 승격했다.

### 오프셋이 틀리면 탭이 백지가 된다

이 태스크에서 가장 위험한 부분이었다. 리뷰가 독립적으로 검증했다: 추출된 문서의
오프셋 배열이 **UTF-8 / CP949 / UTF-16LE / UTF-16BE / UTF-16LE+CRLF 전부에서**
`indexer::scan_offsets`와 byte-identical이었다. `total_bytes == source.len()`,
`Phase::Complete`, 마지막 행의 `line_range`가 `total_bytes`로 떨어지는 것까지 확인.

BOM은 안 붙인다. `encode_bytes`는 BOM을 내지 않고(`write_file`만 옵션에 따라 낸다),
`decode_line`은 있으면 벗긴다. 그래서 offset 0이 진짜 0번 행이다.

### 고친 것

- **추출 탭에서 Ctrl+S를 누르면 매번 파일 선택창이 다시 떴다.** 경로가 비어 있어
  파일 선택창으로 폴백하는 것까지는 맞는데, `save_as == false`라서 성공 후
  `doc.path`를 갱신하지 않았다. 파일은 제대로 써지는데 탭은 계속 추출본인 척하고,
  저장할 때마다 경로를 다시 입력해야 했다.
  `save_as_fallback(save_as, cur_path_empty)` 순수 함수를 폴백 분기와 경로 갱신
  분기가 공유하게 했다
- 저장 테스트 2개가 진짜 술어를 복붙/하드코딩해서 이 결함을 못 잡고 있었다.
  같은 순수 함수를 부르게 고쳤다
- 파일명이 실제로 `"[hit] "`로 시작하면 오라벨이 됐다. 라벨 텍스트를 킁킁대는
  대신 `Document::is_extracted` 불리언을 뒀다

## 이번에 반복된 교훈

### 테스트가 가드를 복붙하면 가드를 검증하지 못한다

A·B·C 세 태스크에서 **연달아** 같은 결함이 나왔다. 테스트가 `update()` 안의 가드
표현식을 그대로 베껴 쓰고 자기 사본이 false인지 확인한다. 진짜 가드를 지워도
테스트가 통과한다.

egui 클로저 안의 판단은 **순수 자유 함수로 뽑아서** `update()`와 테스트가 같은
함수를 부르게 해야 한다. 이 코드베이스에 이미 그 관례가 있었는데
(`needs_big_op_confirm`, `next_cell_drag_active`) 새 코드에서 지켜지지 않았다.
지금은 `plan_dropped_files`, `find_keys_live`, `extract_plan`, `extract_allowed`,
`extract_button_enabled`, `save_as_fallback`, `tab_label`, `table_col_count`가
모두 그 형태다.

Task D에서는 구현자가 **mutation testing**으로 직접 확인했다 — 가드를 지우고
테스트를 돌려서 실제로 깨지는지 봤다. 이게 맞는 방식이다.

### 모달이 아닌 창은 상태를 얼리지 않는다

egui 0.28에는 `Window::modal()`이 없다. "확인 창이 떠 있으니 사용자가 다른 걸
못 만지겠지"는 **틀린 가정**이다. 위치 인덱스를 들고 기다리는 pending 동작은 그
사이에 대상이 움직이면 엉뚱한 걸 건드린다. 대기 중에는 대상 집합을 명시적으로
얼려야 한다.

### 없는 API를 가정하지 않는다

이번엔 쓰기 전에 레지스트리 소스를 읽었다. `RawInput::take()`의 `mem::take`,
`Painter`에 상호작용 메서드가 없다는 것, `TableBuilder::scroll_to_row`가
`at_most(total_rows-1)`로 클램프한다는 것 모두 소스에서 확인했다.

## 남은 것

### 알려진 한계

- **뷰 모드 찾기는 인덱서가 도달한 행까지만** 훑는다. 10GB 파일을 열자마자
  검색하면 아직 인덱싱 안 된 뒷부분의 매치를 "Not found"라고 답하고, 그 이유를
  설명하지 않는다. 추출도 같다
- **Replace All / 행 추출이 수백만 행에서 한 프레임을 블록**한다. 정확하고
  되돌릴 수 있지만 반응이 없다. 확인 다이얼로그를 붙이지 않기로 했다 —
  추출은 원본을 안 건드리므로 되돌릴 것도 없다
- `clear_cells`가 값이 있는 컬럼에서 여전히 200만 행에 ~24초 (이전 작업에서 이월)
- `save_enc`/`save_bom`/`clipboard_cache`/`error`가 `App` 수준이라 문서별이 아니다.
  잠금 가드로 막았을 뿐 구조를 바꾸진 않았다
