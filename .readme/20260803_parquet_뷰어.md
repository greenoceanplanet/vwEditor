## 1. 핵심 판단 — 네 번째 문서 종류가 아니다

Parquet 문서를 `render_hex`처럼 전용 렌더 경로로 만들 수도 있었다. 그러면 기존
코드를 전혀 안 건드린다. 대신 찾기·정렬·내보내기·셀 선택·복사를 **전부 새로
써야 한다.**

코드를 읽어 보니 이음매가 이미 있었다:

```rust
pub fn logical_line(doc: &Document, logical: usize) -> Option<String> {
    if let Some(e) = &doc.edit { e.lines.get(logical).cloned() }
    else if let Some(p) = &doc.parquet { p.borrow_mut().row_line(logical, b',') }  // 추가한 한 줄
    else { decode_logical_line(doc, logical) }
}
```

호출부가 25곳이고, 찾기는 `find.rs`에 `get_line` 클로저를 넘기며(그래서 `find.rs`는
Source도 mmap도 모른다), 내보내기는 `save::write_file(&[String])`로 포맷 무관이다.
**Parquet을 "네 번째 문서 종류"가 아니라 "표 문서의 세 번째 데이터 출처"로 보면**
갈래 하나로 표 렌더링·찾기·내보내기가 따라온다.

`RefCell`을 쓴 것은 타협이다. 행 조회가 row group 캐시를 갱신해 `&mut`가 필요한데
`logical_line`은 `&Document`를 받는다. 시그니처를 바꾸면 호출부 25곳이 전부 깨진다.

**정렬만 이 이음매를 우회한다.** `sort.rs`가 `source.as_bytes()`로 mmap 원본을 직접
훑기 때문이다(15M행 정렬이 빠른 이유). Parquet에는 구분자로 나뉜 원본 텍스트가
존재하지 않아 별도 경로가 됐다 — 대신 컬럼 지향의 이점을 쓴다. 정렬 키 컬럼만
읽고 나머지는 디코드조차 하지 않는다.

## 2. 같은 함정을 다섯 번 만났다 — "인덱서가 돈다"는 전제

Parquet 문서는 개행을 셀 필요가 없어 **인덱서를 띄우지 않는다.** 이 사실 하나에서
두 갈래의 전제가 무너진다:

- `LineIndex`가 영영 비어 있어 **`line_count()`는 0**이다.
- `Phase`가 영영 **`Priming`**이라 `Phase::Complete`가 참이 되지 않는다.

그런데 그 두 값을 직접 보는 코드가 여러 군데에 흩어져 있었다. 하나씩 발견할
때마다 그게 마지막인 줄 알았다:

| # | 위치 | 전제 | 증상 |
|---|---|---|---|
| 1 | `scan_rows_scoped` | `line_count()` | 찾기가 **조용히 0건** |
| 2 | `table_col_count` | `line_count()` | 헤더를 못 읽어 컬럼이 **1개로 무너짐** |
| 3 | `render_table`의 `total_lines` | `line_count()` | `data_rows`가 0이라 **표가 통째로 빔** |
| 4 | `render_text`의 `total_lines` | `line_count()` | (표 모드라 도달 안 하지만 통일) |
| 5 | 정렬 메뉴·툴바 | `Phase::Complete` | **정렬 버튼이 끝내 안 켜짐** |

1~4는 `doc_line_count(doc)`로, 5는 새로 만든 `doc_rows_ready(doc)`로 모았다. 둘 다
"편집 버퍼·Parquet·mmap 세 출처를 모두 아는 한 곳"이고, 텍스트 경로에서는 종전과
같은 값이라 **기존 동작이 바뀌지 않는다.**

**교훈은 "다섯 곳을 고쳤다"가 아니다.** 같은 개념(문서의 행 수 / 데이터 준비
여부)을 얻는 방법이 여러 갈래로 흩어져 있었고, 새 데이터 출처가 생기자 그 분산이
한꺼번에 드러났다. 세 번째를 고칠 때 `grep`으로 전수 조사를 했어야 했는데 네
번째까지 가서야 했고, **다섯 번째는 아예 놓쳤다.**

특히 1번과 5번이 무서운 종류다 — **오류가 나지 않는다.** 찾기가 0건을 돌려주고,
"찾기가 동작한다"만 확인하는 테스트는 그대로 통과한다.

## 3. 완성했다고 보고한 뒤에 드러난 것 — 죽은 기능

내가 "구현 완료, 815 테스트 통과"라고 보고한 뒤, 사용자가 물었다.
**"근데 csv로 익스포트는 안 돼?"**

확인해 보니 **기능이 통째로 죽어 있었다.** `collect_export_lines`도, 저장 경로의
Parquet 분기도, 그 둘을 검증하는 테스트도 전부 있었다. 그런데 메뉴가 잠겨
**한 번도 불리지 않았다.**

`doc_savable`이 편집 버퍼를 요구하는데 Parquet은 읽기 전용이라 버퍼가 없다.
Save/Save As가 둘 다 회색이었다.

이 문서에 필요한 것은 "제자리 저장"이 아니라 "다른 이름으로 내보내기"다. 개념을
갈랐다:

- `doc_savable` — 제자리 저장. Parquet은 **거짓**(읽기 전용 파일을 덮어쓸 수 없다).
- `doc_exportable` — 다른 이름으로 내보내기. Parquet은 **참**.

메뉴 항목 이름도 Parquet일 때는 `Export as CSV/TSV…`로 바꿔 무엇을 하는지 드러냈다.

그리고 물어본 김에 정렬도 확인했더니 **그것도 막혀 있었다**(위 표의 5번).

**같은 실수의 반복이다.** 함수는 완벽히 테스트하고 배선은 안 봤다. 이번 작업에서
변이 테스트로 이미 한 번 겪은 것인데(§8), 그때는 렌더 호출 배선만 보고 **메뉴
게이트는 보지 않았다.** 테스트가 부르는 경로와 사용자가 지나는 경로가 다르면,
테스트는 통과하면서 기능은 없는 상태가 된다.

그래서 이번엔 게이트 자체를 겨누는 테스트를 넣었다 —
`doc_exportable`/`doc_rows_ready`/`text_*`가 Parquet에서 각각 무엇을 답해야 하는지.
종단 테스트에도 "UI가 이 기능에 닿는가" 단언을 붙이고, 내보낸 CSV를 실제 파일로
써서 5001줄이 나오는지·컬럼 수가 유지되는지까지 본다.

## 4. 게이트 하나를 셋으로 갈랐다

`text_tools_enabled(doc) = doc.hex.is_none()`이 이미 있었다. Parquet도 "텍스트가
아닌 문서"이니 여기 얹으면 될 것 같았다.

얹었더니 **정렬이 죽었다.** 그 플래그가 Tools 메뉴 전체를 잠그는데, 정렬은 이번에
만든 기능이다.

세 가지 서로 다른 질문이 한 이름에 묶여 있었다:

| 질문 | 헥스 | Parquet |
|---|---|---|
| Tools 메뉴(정렬)를 쓸 수 있나 | 아니오 | **예** |
| 편집할 수 있나 | 아니오(자체 경로) | 아니오 |
| 구분자 선택·인덱싱 문구가 의미 있나 | 아니오 | 아니오 |

하나로 묶으면 반드시 하나가 틀리는 구조라 `text_tools_enabled` /
`text_edit_allowed` / `text_layout_tools_enabled` 셋으로 갈랐다. 셋이 서로 다른
답을 내는 것 자체를 테스트로 박았다.

## 5. 스펙을 쓰고 나서 스펙을 검토했다

스펙을 커밋한 뒤 코드와 대조하며 다시 읽었더니 **내가 확인하지 않고 쓴 가정 넷이
틀렸다**(`52b2184`). 구현 전에 잡아서 다행인 것들이다.

가장 위험했던 것은 **순열 좌표계**다. 스펙에 "헤더를 제외한 데이터 행의 순열"이라
썼는데 실제는 반대였다. `app.rs:2759` 주석과 `:13824` 테스트가 명시한다 —
`permutation[view_row] = 논리 행번호`이고 **절대 논리 행번호(헤더 포함)**다.
인덱스는 0-based 화면 행, 값은 1-based 논리 행이라는 비대칭이다. 그대로
구현했으면 정렬할 때마다 모든 행이 하나씩 밀렸을 것이다.

나머지 셋: 개행 처리(인용만으로 부족 — §6), 찾기의 0건 함정(§2의 1번), 게이트
위치(호출부마다가 아니라 함수 안에서 막기).

**그래도 §2의 5번과 §3은 못 잡았다.** 스펙 검토는 "내가 쓴 것"과 "코드"를
대조하는 일이라, **스펙에 아예 없던 것**(메뉴가 이 문서 종류에 닿는가)은 시야에
들어오지 않았다.

## 6. 왕복은 되는데 화면이 깨지는 것 — 개행

`join_row`로 이어 붙인 줄을 `split_fields`가 되돌리지 못하면 표의 모든 컬럼이
어긋난다. 그래서 왕복 자체를 계약으로 박았고(구분자·따옴표·한글·탭·`"""` 등
11케이스), 프로브로 **셀 안의 개행도 정확히 복원되는 것**을 확인했다.

그런데 왕복이 되는 것과 화면이 멀쩡한 것은 다른 문제였다. 텍스트 경로는
`decode_logical_line`이 `trim_end_matches(['\r','\n'])`로 개행을 제거하므로
**"한 줄에 개행이 없다"가 표 렌더링의 전제**인데, Parquet 문자열 셀에는 들어갈 수
있다. 그대로 두면 egui가 여러 줄 galley를 만들어 행 높이와 정렬이 어긋난다.

CR/LF를 공백으로 치환한다. 손실 변환이지만 읽기 전용이라 원본은 안전하고, 화면과
내보내기 결과가 일치한다.

## 7. 손으로 만들려다 그만둔 것들

**타입별 포맷.** 스펙에 timestamp·decimal·date 표시 규칙을 표로 정리해 뒀는데,
프로브를 돌려 보니 `arrow_cast::display::ArrayFormatter`가 이미 그 형태로 낸다 —
`2026-04-01T08:33:20+09:00`, `1234.56`, `2024-10-04`. 직접 구현하면 이걸 재현하려다
틀릴 뿐이다. 덮어쓴 것은 둘뿐이다(바이너리는 16진수 덤프 대신 요약, null은 계약
방어용).

**geo JSON 파싱.** "의존성을 아끼려고 `columns` 키만 뽑는 최소 스캔"을 생각했다가
철회했다. 이스케이프된 따옴표(`"my\"col"`) 하나만 잘못 처리해도 멀쩡한 문자열
컬럼을 geometry로 오인해 `<binary>`로 표시한다. 신뢰 경계에 검증 안 된 파서를
두는 것이 크레이트 5개보다 비싸다.

## 8. 변이 테스트가 잡은 것

9건을 돌려 6건이 죽고 2건이 살아남았다.

**캐시 키에서 컬럼 집합을 빼도 통과했다.** 무효화가 두 겹인데(`set_visible_columns`의
`clear`와 `CachedGroup.cols` 키) 1차가 항상 먼저 비워서 2차는 테스트에서 한 번도
일하지 않았다. 1차를 우회해 2차만 겨누는 테스트를 추가했다.

**두 번째 생존에서 내 근거가 틀린 것을 발견했다.** 스펙과 주석에
"`ArrayFormatter`가 null을 `<null>`로 낸다"고 적었는데 사실이 아니었다. 기본
`FormatOptions`는 이미 빈 문자열로 낸다 — 앞선 프로브에서 `<null>`을 본 것은 내가
그 마커를 직접 출력했기 때문이다. 분기는 남기되(옵션 기본값에 기대는 것이므로)
근거를 사실에 맞게 고쳐 적었다.

## 배운 것

1. **함수가 맞아도 사용자에게 닿지 않으면 없는 기능이다.** 내보내기는 코드도
   테스트도 완성돼 있었는데 메뉴가 잠겨 한 번도 불리지 않았다. "완성했다"고
   보고까지 한 뒤 사용자의 한 마디("csv로 익스포트는 안 돼?")에 드러났다.
   **기능을 마쳤다고 말하기 전에 사용자가 지나는 경로를 끝까지 따라가 볼 것.**

2. **오류 없이 조용히 틀리는 버그가 가장 비싸다.** 찾기가 0건을 돌려주고, 정렬
   버튼이 안 켜지는데, 어느 쪽도 오류를 내지 않고 테스트는 통과했다. "동작한다"가
   아니라 "올바른 값을 낸다"를 물어야 한다.

3. **같은 개념을 얻는 방법이 흩어져 있으면 새 출처가 생길 때 한꺼번에 터진다.**
   "행 수"와 "데이터 준비 여부"를 얻는 코드가 다섯 곳에 각자 있었고 다섯 번 다
   고쳐야 했다. 세 번째에서 `grep`으로 전수 조사를 했어야 했는데, 그러지 않아
   다섯 번째는 사용자가 찾아 줬다.

4. **플래그 하나에 질문 셋을 묶으면 반드시 하나가 틀린다.** 헥스와 Parquet은
   "텍스트가 아니다"라는 점에서 같았지만 정렬 가능 여부에서 갈렸다. `doc_savable`도
   "저장"과 "내보내기"를 한 이름으로 묶고 있었다.

5. **스펙을 쓴 뒤 코드와 대조하면 내가 쓴 가정이 틀린 것이 나온다.** 넷을 찾았고
   그중 순열 좌표계는 구현했으면 모든 행이 밀렸을 것이다.

6. **라이브러리가 이미 하는 일을 손으로 다시 하지 말 것.** 타입 포맷은
   `ArrayFormatter`가, JSON은 `serde_json`이 한다. 둘 다 처음엔 직접 하려 했다.
