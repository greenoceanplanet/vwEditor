## 1. 10MB 이하는 열자마자 편집 모드

`AUTO_EDIT_MAX_BYTES = 10MB` 이하면 `open_path`가 곧바로 `enter_edit_mode`를
부른다. 10MB는 "읽는 값"이 아니라 **기다림의 값**이다 — 편집 버퍼 로드는
동기라 그 시간만큼 UI가 멈추는데, 실측(릴리스, 9.0MB/34.6만 행 CSV)으로
`open_path` 전체가 **첫 회 21ms, 이후 8ms**. 상한에서도 한 프레임 안이다.
반대쪽 극단(10GB)은 편집 버퍼가 수억 개의 `String`이 되므로 상한이 필요하다.

판정은 크기 하나만 본다. 인덱싱 완료를 기다리지 않는 이유: 편집 모드에서는
`edit.lines`가 진실이고 mmap 인덱스는 화면이 보지 않는다. 구분자/헤더도 안
본다 — 표냐 텍스트냐는 *보기* 방식이지 편집 가능 여부가 아니다.

**부수 효과가 본 작업만큼 컸다.** "파일을 열면 뷰 모드"라는 전제를 깔고 있던
기존 테스트 11개가 일제히 깨졌다. 각자 `exit_edit_mode`를 흩뿌리는 대신
`view_doc` 헬퍼로 의도를 이름에 남겼다 — 이 테스트들이 보려는 것은 **mmap
경로**이지 "편집 모드가 아닌 상태"가 아니기 때문.

**테스트로 못 잡는 변이 하나를 주석으로 남겼다.** `enter_edit_mode(doc)` 호출을
`doc.edit = Some(load_edit_buffer(..))` 인라인 대입으로 바꿔도 아무 테스트도
안 깨진다 — 갓 만든 `Document`는 `sort`/`row_errors`가 이미 `None`이라 두
구현이 **관측 가능하게 구별되지 않는다**. 테스트 구멍이 아니라 코드의 성질이라,
가짜 차이를 만드는 테스트 대신 호출부 주석에 그 사실을 명시했다.

## 2. 인자 없이 실행하면 빈 새 파일 (+ File→New / Ctrl+N)

메모장처럼 열자마자 타이핑. 핵심 발견 두 가지:

**저장 유도는 새로 만들 게 없었다.** 빈 `path` 하나가 전부다 —
`save_as_fallback`이 빈 경로를 보고 파일 선택 창으로 폴백하고, 저장 성공 뒤
같은 판정으로 `doc.path`를 갱신해 다음 Ctrl+S는 덮어쓰기가 된다. 추출본
탭(`[hit]`)이 이미 지나다니는 검증된 길이다. 같은 이유로 `new_document`는
`build_extracted_doc`을 재사용했다 — 필드 40개짜리 구조체 리터럴을 한 벌 더
두면 `Document`에 필드가 늘 때 한쪽만 고쳐질 자리가 생긴다.

**시작 판단을 `main`에서 `App::start`로 옮겼다.** 변이 테스트에서 "인자 없을
때 새 문서 안 만듦"이 살아남았기 때문 — `main()`은 테스트가 부를 수 없어
검증 구멍이었다. 옮기면서 별도 결함이 드러났다: **열기에 실패하면 탭이 하나도
없어 창이 텅 비었다.** 이제 그 경우에도 빈 새 파일을 띄우고 에러는
`self.error`가 따로 전한다.

메뉴 클릭과 Ctrl+N은 `open_new_tab` 하나를 함께 지난다. 메뉴 쪽은 egui 클로저
안이라 테스트가 구동할 수 없으므로, 같은 함수를 지나야 "새 탭으로 붙는다
(기존 탭을 갈아치우지 않는다)"가 한 번의 검증으로 양쪽에서 지켜진다.

## 3. 줄 끝 개행 기호 — 두 모드의 정확도가 다르고, 그 차이는 없앨 수 없다

`parse::LineEnding { None, Lf, CrLf, Cr }` + `split_line_ending`(바이트 꼬리
판정). 파일 전체의 `edit::Newline`과 **다른 층위**다 — 그쪽은 "저장할 때
무엇으로 쓸까", 이쪽은 "이 줄이 무엇으로 끝났나".

| | 줄별 개행 | 섞인 파일 |
|---|---|---|
| 뷰 모드(mmap) | 진짜 값 (행 범위가 개행 바이트를 포함) | 있는 그대로 |
| 편집 모드 | 파일 전체 스타일로 근사 | 전부 같은 기호 |

편집 모드가 근사인 이유는 표시의 한계가 아니라 **편집 버퍼가 그 정보를 보관하지
않는다**는 불변식의 결과다(`lines[i]`에 개행 없음, 로더가 떼면서 파일 단위
플래그 하나만 남김). 저장도 같은 스타일로 통일해 쓰므로 화면이 곧 저장 결과와
일치한다. **마지막 줄**은 종결 개행이 실제로 있을 때만 기호가 붙는다 — 없는
개행을 그리면 거짓말이고, 편집 버퍼는 그 정보가 없으니 안 붙인다.

**기호는 한 차례 뒤집혔다.** 처음엔 사용자 요청대로 CRLF를 두 글자(`␍␊`)로
그렸는데, 실제로 보니 "엔터 하나에 두 개가 들어가는" 것처럼 읽혔다. 결론은
관행대로 **꺾인 화살표(`↵`) 하나** — CRLF냐 LF냐는 어느 줄에나 같은 **파일
단위 성질**이라 줄마다 기호 개수로 알릴 정보가 아니고, 그 답은 저장
다이얼로그가 이름으로 말한다. 단 `\r` 단독(옛 Mac/깨진 파일)만은 `␍`로
남겼다 — 파일 스타일이 아니라 "**이 줄만 이상하다**"는 신호라, 같은 화살표면
그 이상이 화면에서 사라진다.

렌더링 규칙 하나가 캐럿 정확성을 지킨다: **기호는 본문 galley 바깥에 따로
그린다.** 이 코드는 galley 하나가 char↔x 매핑의 유일한 진실이라(`x_of` /
`cursor_from_pos`), 기호가 galley에 들어가면 존재하지 않는 글자 위에 캐럿이
서고 줄 끝 클릭이 기호 안으로 빨려 들어간다. 폰트에 U+240x/U+21B5가 없으면
두부(□) 대신 `\r\n` 이스케이프로 폴백하는데, 폰트 조회는 `Context`가 필요해
테스트가 못 만들므로 `has_glyph`를 인자로 받는 순수 함수(`ending_glyphs`)로
분리했다.

## 4. 저장 시 개행 선택 (Save / Save As 공통)

Enter는 원래도 문자를 넣지 않는다 — `split_line`이 `Vec<String>`을 둘로 나눌
뿐이다. 실제 개행 바이트는 저장 때 `EditBuffer.newline` 하나로 결정되는데,
인코딩/BOM은 다이얼로그에 있으면서 개행만 고를 수 없었다.

`Line ending` 콤보를 추가했다. 라벨은 `CRLF (Windows)` / `LF (Unix/Linux/macOS)`
— 고르는 기준은 대개 "어디서 쓸 파일인가"이고 CRLF/LF만으로는 답이 안 된다.
기본값은 **원본과 같은 스타일**(저장이 개행을 조용히 바꾸면 diff가 전 줄로
번진다). 저장 성공 시 고른 값을 편집 버퍼에 **되쓴다**(`apply_save_newline`) —
안 되쓰면 파일은 LF인데 화면 기호는 CRLF를 그려 화면이 파일을 설명하지 못한다.
dirty는 건드리지 않는다(저장 직후라 버퍼=파일인데 켜면 "저장 안 됨"이 된다).

변이 테스트가 위험한 자리를 하나 찾았다: 저장 옵션의 개행을 다이얼로그
(`app.save_newline`)가 아니라 문서에서 읽어도 **아무 테스트도 안 깨졌다** —
`init_save_defaults`가 둘을 같은 값으로 맞춰 두기 때문에, 콤보에서 **다른
값을 골랐을 때만** 조용히 무시되는 구조였다. `save_options`로 추출하고 정확히
그 어긋난 경우를 테스트로 못박았다.

## 5. 한글이 아예 안 들어가던 문제 (IME)

**원인:** 한글/일본어/중국어는 `Event::Text`가 아니라 `Event::Ime`로 들어오는데,
입력 수집기가 `Text`만 보고 있어 조합 입력이 통째로 버려졌다.

고칠 곳이 둘이고 **둘 다 있어야** 동작한다:

1. `ImeEvent::Commit` → `Insert` 인텐트. 확정 문자는 곧 텍스트 삽입이므로
   기존 경로(선택 삭제 + undo)를 재사용한다.
2. `output.ime`에 캐럿 위치 채우기(`set_ime_output`). **이게 위치 통보가 아니라
   IME를 켜는 스위치다** — egui-winit이 `let allow_ime = ime.is_some()`으로
   판단한다(lib.rs:831). 이 앱은 `TextEdit` 없이 본문을 직접 그리므로
   `TextEdit`이 하던 이 일을 대신 해야 한다. 빠지면 조합 창이 엉뚱한 자리에
   뜨는 정도가 아니라 IME가 활성화 자체가 안 된다.

**조합 중 표시는 판단이 한 번 뒤집혔다.** 처음엔 Preedit(ㅎ→하→한)을
버렸다 — undo 스택이 낱글자로 오염되는 것을 피하려고. 그런데 IME 자체 창에만
뜨고 본문에는 안 보여서, 사용자 기대("초중종성 단위로 다 보여야")와 어긋났다.
최종 구조는 `Document.ime_preview`: **버퍼가 아니라 화면 전용** 문자열로 받아
캐럿 자리에 밑줄과 함께 덧그린다. 버퍼·undo·dirty 어디에도 안 들어가므로
Ctrl+Z 단위는 확정 글자로 유지되고, 조합만 해도 dirty가 켜지는 일이 없다.
확정(Commit)이나 조합을 깨는 다른 인텐트가 오면 미리보기를 지운다 — 안 지우면
확정 글자가 버퍼와 미리보기에 둘 다 있어 화면에 두 번 나온다.

## 6. Tab — 네 번 만에 끝난 이유

이번 세션에서 가장 비쌌던 버그. 요구는 단순하다: "편집 중 Tab은 탭 문자다."
그런데 egui의 포커스 순회와 정면으로 충돌했고, 수정마다 다음 층이 드러났다.

**1차 (`10e27c6`): 인텐트 + 소비.** `collect_text_intents`에 Tab 분기를 넣고
`consume_key`로 이벤트를 지웠다. 테스트 통과. → 사용자: "아직도 안 된다."

**2차 (`629ee81`): 자기 차단 발견.** 1차 테스트는 헬퍼를 직접 불러
**포커스 게이트를 건너뛰었다**. 실제로는: 소비 안 된 첫 Tab이 포커스를 툴바로
옮김 → `keyboard_free`가 거짓 → 본문이 키를 안 받음 → **소비 코드 자체가
다시는 실행 안 됨**. Tab이 자기 자신을 막는 구조였다. 소비를 게이트 밖으로
빼고, Tab은 게이트를 타지 않게 했다(게이트의 목적은 "입력란 글자 중복 방지"인데
Tab은 글자를 안 넣으므로 중복될 게 없다). 덤: `consume_key`는
`matches_logically`라 **Shift를 무시**해 Shift+Tab까지 먹는다 — 수식어를 직접
확인하는 수동 retain으로 바꿨다(Shift+Tab은 역방향 순회로 남김).
→ 사용자: "탭은 먹는데 포커스가 File로 간다."

**3차 (`843c639`): 프레임 시작 타이밍.** egui는 **프레임이 시작될 때**
RawInput에서 Tab을 읽어 `give_to_next`를 켠다(memory.rs:444-462). 프레임 도중
이벤트를 지워도 이미 늦고, 그 프레임에 처음 등록되는 focusable 위젯이 포커스를
가져간다(memory.rs:543) — 메뉴바가 본문보다 먼저 그려지므로 File 버튼이었다.
소비를 `update()` 맨 앞으로 옮기고, UI를 다 그린 뒤 포커스를 걷어냈다.
→ 사용자: "누를 때마다 File 하이라이트가 깜빡이고 느리다."

**4차 (`821a508`, 최종): 선점.** 3차의 "그린 뒤 걷어내기"는 File이 한 프레임
동안 **실제로 포커스를 받아 하이라이트를 그린 뒤에야** 지우는 구조라 깜빡임이
남고, 포커스 변화가 리페인트를 하나 더 유발했다. 최종 해법은 `give_to_next`를
**선점**하는 것 — `interested_in_focus`가 public이므로, 본문이 Tab을 먹는
프레임에는 어떤 패널보다 먼저 더미 id(`body_tab_sink`)를 등록해 플래그를
소진시키고 곧바로 포커스를 비운다. File 차례에는 플래그가 꺼져 있어
**하이라이트 프레임 자체가 생기지 않는다**.

회귀 테스트가 4차에서 오히려 단순해졌다: 정리 단계 없이 메뉴바→본문 순서로
한 프레임을 돌린 뒤 **포커스가 None이면 File이 애초에 못 받은 것**이다
(받았다면 아무도 안 지웠으니 남아 있어야 한다).

Tab을 먹는 조건은 `wants_tab_character` 하나에 모였다: 편집 모드 + 텍스트
모드(표 모드는 셀에 탭이 들어가면 TSV 필드가 갈라진다) + 다이얼로그 없음 +
포커스 없음(툴바 입력란이 포커스를 쥔 Tab은 입력란을 **벗어나는** 순회여야
한다 — 가로채면 갇힌다).

## 7. 저장/열기 확장자 목록

**저장**(`save_filters`)은 첫 항목이 다이얼로그의 기본 선택이라 순서가 곧
동작이다: ①현재 파일 확장자 → ②보기 구분자 순으로 고른다. `data.tsv`를
저장하는데 기본이 `.csv`면 실수로 형식이 바뀐다. 어느 쪽으로 골라도 나머지
형식과 `All files`를 항상 남긴다(.json/.md도 저장할 수 있어야 한다).
**열기**는 반대로 넓은 것 먼저 — 무엇을 열지 모르니 `Text/CSV/TSV` 묶음이
첫 항목이다. TSV는 양쪽 다 `.tab`도 받는다(`detect_separator`가 그 확장자를
탭으로 연다).

## 8. 검증

- 테스트 **587 → 658** (+71), 전 구간 0 실패 유지
- clippy 25 warnings — 세션 전 기준선과 동일(제가 만든 3건은 즉시 정리)
- 변이 검사 라운드별: 자동 편집 6종(1 관측불가—주석화), 새 파일 10종,
  개행 기호 10종, IME+개행선택 11종, Tab 1차 12종, Tab 2차+필터 9종,
  Tab 3차 6종, Tab 4차 3종 — **관측 가능한 변이 전부 격리**
- 실측: 9MB 자동 편집 진입 8~21ms, 11MB 뷰 모드 0.1ms

## 배운 것

- **"테스트는 통과하는데 사용자는 안 된다"가 두 번 나왔고, 원인이 같았다.**
  헬퍼를 직접 부르는 테스트는 실제 경로의 게이트(`keyboard_free`)와 렌더
  순서(메뉴바 먼저)를 건너뛴다. 회귀 테스트는 **실제 프레임 순서를 그대로
  태워야** 한다 — Tab 2차와 3차 모두, 실제 순서를 태우는 테스트를 쓰자마자
  즉시 재현됐다.
- **egui 포커스는 프레임 시작에 결정된다.** `begin_frame`이 RawInput에서 Tab을
  읽어 `give_to_next`를 켜므로, 프레임 도중의 이벤트 제거로는 순회를 못 막는다.
  막는 방법은 선점(`interested_in_focus`)뿐이고, 그것도 어떤 패널보다 먼저여야
  한다. 또 `consume_key`는 `matches_logically`라 Shift/Alt를 무시한다.
- **`output.ime`는 위치 통보가 아니라 스위치다.** egui-winit이
  `ime.is_some()`으로 `set_ime_allowed`를 결정한다. 커스텀 텍스트 렌더링을
  하면 `TextEdit`이 조용히 해 주던 일들이 전부 내 몫이 된다.
- **화면 전용 상태라는 층이 유용하다.** IME 미리보기(`ime_preview`)와 개행
  기호는 버퍼·undo·dirty·저장 어디에도 안 들어가는 표시 전용이다. 이 층을
  버퍼와 섞으면 undo 오염·가짜 dirty·캐럿 어긋남이 한꺼번에 온다.
- **변이가 못 죽는 자리는 두 종류다.** GUI 클로저 안(→ 판정을 함수로 추출:
  `wants_tab_character`, `text_frame_intents`, `mark_saved`, `save_options`)과
  관측 가능한 차이가 없는 것(→ 테스트 대신 주석으로 사실을 명시).
