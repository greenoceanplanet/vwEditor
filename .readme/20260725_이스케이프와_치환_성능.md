## 요약

찾기 입력란에 `\t`를 칠 수 있게 하는 작은 요청으로 시작했는데, 사용자가 실제
데이터로 바꾸기를 돌려 보면서 **성능 문제가 두 단계로 드러났다.**

최종: 1,542만 행 TSV에서 컬럼 완전일치 Replace All이 **21초 → 0.21초 (약 100배)**.
EmEditor 수치(0.3초)를 넘어섰다.

그 과정에서 **"Rust라서 느리다"는 통념이 틀렸다는 것**과, 병목이 알고리즘도
언어도 아닌 **Windows 기본 힙 할당자**였다는 것을 측정으로 확인했다.

## 1. 이스케이프 시퀀스

사용자 요청: *"찾고 바꿀 때 tab 문자도 입력 가능하게. 아스키 코드를 쓰는 규칙을
정하면 되겠다."*

**바꾸기(Replace / Replace All)는 이미 있었다** — 편집 모드 전용, undo 지원까지.
그래서 실제 작업은 이스케이프 시퀀스 하나였다.

### 규칙

찾기 창의 `Escape sequences` 체크박스 (**기본 꺼짐**):

| 입력 | 결과 |
|---|---|
| `\t` | 탭 |
| `\\` | 백슬래시 하나 |
| `\xNN` | 그 문자 코드(16진수 2자리) |
| 그 외 (`\n`, `\z` …) | **글자 그대로** — 오류 안 냄 |

기본을 끈 이유: `C:\temp` 같은 값을 그대로 찾는 경우가 흔하다. EmEditor·VS Code도
같은 방식이다.

### `\n`을 뺀 이유

이 프로그램은 문서를 **행 배열**(`Vec<String>`)로 다루고 **`lines[i]`에는 절대
개행이 없다**. 그 불변식이 표 행번호·정렬·저장 전체를 떠받친다. 찾기도 행 단위라
`\n`은 행의 **경계**이지 내용이 아니다.

그러므로 "줄바꿈 없애기"는 찾기/바꾸기가 아니라 **행 병합**이라는 다른 기능이다.
필요해지면 그때 별도로 만들기로 했다.

다만 `\n`을 **오류로 만들지도 않았다** — 백슬래시+`n` 두 글자로 남아 그냥 그
두 글자를 찾을 뿐, 아무것도 깨지지 않는다.

### 배선이 진짜 작업이었다

디코딩 자체는 30줄이다. 위험한 건 `find_query`/`replace_text`를 **소비하는 10곳**을
빠짐없이 통과시키는 것이었다. 하나라도 날 문자열을 쓰면 "Find Next는 탭을 찾는데
Find All은 못 찾는" 식으로 조용히 갈린다.

`effective_query()` / `effective_replacement()` 접근자를 만들어 전부 통과시켰다.
버튼 활성 조건과 F3 빈 검색어 가드만 의도적으로 날 문자열을 쓴다 — 그건 "사용자가
입력란에 뭘 쳤는가"를 보는 것이므로 맞다.

**구현자가 브리프에 없던 함정을 잡았다**: 브루트포스 비교 테스트 3개가
`doc.find_query`를 직접 쓰고 있어서, 이스케이프를 켜면 "빠른 스캔 == 브루트포스"라는
정확성 계약 검증이 **조용히 무의미해질 뻔했다.**

## 2. 바꾸기 성능 — 두 단계

### 1차: 문자열 판정 → 바이트 판정 (21초 → 1.8초)

사용자: *"리플레이스 엄청 오래 걸리네? 3열에서 `-`를 '한국어'로 고치는데 10초 더."*
그리고 곧바로: *"바이트 수준에서 치환해야 빠를껄"*

정확한 지적이었다. 측정(앱의 실제 코드를 벤치에 복사):

```
1,542만 행, needle "-", rep "한국어", WholeCell, ignore_case
매치: 476만 행 (전체의 31% — "-"가 흔한 값이었다)

판정 (find_in_line_scoped)     : 17,603 ms   ← 병목
  ↳ 그중 split_fields          :  8,533 ms   (1억 2,341만 필드를 String 할당)
순수 문자열 조립                :    405 ms   ← 진짜 작업은 이것뿐
```

**실제 치환은 0.4초인데 판정에 17.6초를 썼다.** 스캔 경로는 앞선 작업에서 바이트로
고쳤는데 **치환 경로만 남아 있었다.**

해결: `replace_cells_bytes` — memchr로 셀 경계를 훑으며 셀 내용이 needle과 같으면
그 구간만 갈아 끼운다. 따옴표가 있는 행은 기존 경로로 폴백(표시값과 원본 바이트가
다르므로). **21.0초 → 1.8초.**

#### 리뷰가 잡은 Critical

행 안에 **단독 `\r`**이 있으면 csv 파서는 그걸 레코드 종료로 보고(`split_fields`가
1필드) 바이트 경로는 구분자만 보고 쪼갠다(2셀). 결과가 두 방향으로 갈렸다:

- 바꿔야 할 셀을 **조용히 안 바꿈**
- **안 건드려야 할 셀을 바꿔 버림** ← 이게 더 나쁘다. 진짜 편집으로 undo에 들어간다

구형 Mac 개행이나 내보내기 데이터에서 실제로 발생한다. `\r`/`\n`이 있는 행은
폴백하게 고쳤고, 재측정해도 속도 손실이 없었다.

**테스트가 놓친 이유**: 차등 코퍼스 3개의 알파벳(`{a A " ,}`, `{- \t 한 x "}`,
`{É é , a İ K k}`)에 `\r`/`\n`이 없었다. csv 파서가 특수 취급하는 제어 바이트를
빠뜨린 것이다. 이제 넣었다.

### 2차: "EmEditor는 0.3초인데 왜 1.8초?"

사용자의 이 질문이 가장 값진 질문이었다. 남은 1.8초를 쪼갰다:

```
판정만 (prefilter + 셀 경계)    :   554 ms
전체 replace_all                : 1,884 ms
차이 = String 조립/할당          : 약 1,330 ms   ← 70%
```

게다가 `replace_all` **밖에도** 비용이 있었다: 버퍼 반영 867ms + undo 스냅샷 714ms.
앱 전체로는 1.8초가 아니라 **3초 가까이**였다.

사용자 제안으로 조사했다 — *"c++에서 되는데 러스트에서 안되는건지. 빠른 방법이나
라이브러리나 기존 코드들"*.

#### 조사 결과 — 내 가설이 절반 틀렸다

**비용 진단은 맞았지만 처방이 틀렸다.**

| 구성 | Replace All | 배수 |
|---|---|---|
| 현재 (`Vec<String>` + Windows 힙) | 2,626 ms | 1× |
| **+ mimalloc 2줄만** | 916 ms | **2.9×** |
| **+ 핫스팟 수정 (자료구조 유지)** | **309 ms** | **8.5×** |

**Rust 문제가 아니었다. 비용의 61%가 Windows 기본 힙 할당자였다.**
줄당 `String` 하나 = 1,540만 개 할당인데, 그 규모에서 `RtlAllocateHeap`의
락·블록 헤더·흩어진 배치가 지배적이 된다.

#### 전제 두 개가 무너졌다

**Rope는 오히려 11.5배 느리다.** ropey로 직접 측정했다. Rope는 사람이 타이핑하는
국소 편집에 최적화된 자료구조이고, 문서 전체 재작성엔 안 맞는다. ropey 문서 자체가
"대량 변경은 `RopeBuilder`로 선형 재작성하라"고 한다. crop/jumprope의 화려한
벤치마크는 **사람의 타이핑 기록을 재생**하는 것 — 정반대 워크로드다.

**EmEditor도 편법을 안 쓴다.** 저자 공개 벤치가 1.34GB에 0.156초인데, 램에 전부
올려 AVX-512 + 스레드로 정직하게 재작성한 결과다. **저장은 별도 2.4초**로 따로
표기돼 있다. 즉 비교 기준이 공정하고, 우리도 같은 방식으로 이길 수 있다.

### 적용 — 5건, 각각 독립 커밋

| # | 내용 | 효과 |
|---|---|---|
| N-1 | `#[global_allocator]` = mimalloc (2줄) | 2.4배 |
| N-2 | `apply_permutation`의 clone 제거 | **정렬 34.5배** (3,346→97ms) |
| N-3 | `replace_all_in_doc` 3패스 → 1패스 move | 226→46ms |
| N-4 | `replace_all` rayon 병렬화 | 836→157ms |
| N-5 | undo 스택에 바이트 예산 | 메모리 위험 제거 |

**최종: 2,863ms → 207~291ms (약 11배).** 목표 309ms를 넘어섰다.

곁다리 이득이 컸다. mimalloc은 치환뿐 아니라 **파일 열기·정렬·저장·찾기 전부**를
빠르게 한다(모두 할당 집약적). **할당을 하나도 안 하는 판정 패스조차 2배** 빨라졌다 —
`String`들이 촘촘히 모여 캐시 라인과 페이지를 덜 건드리기 때문이다.

#### 메모리는 오히려 줄었다

mimalloc이 30~60% 더 커밋한다는 보고가 있어 확인했는데, 이 워크로드엔 해당하지
않았다. 피크가 **4,881MB → 3,628MB (26% 감소)**. 줄당 String이 작고(평균 58B)
균일해 크기별 슬랩이 Windows 힙의 블록 헤더보다 덜 낭비한다. 나머지 감소는
N-2/N-3가 없앤 임시 사본(약 1.1GB)이다.

#### N-2가 데이터 유실 함정이었다

정렬의 `clone` 제거는 한 줄짜리로 보였지만 아니었다.

`inverse_of`는 order가 정상 순열이 아닐 때 **안 채운 자리에 0을 남긴다**. 그래서
중복 인덱스가 `apply_permutation`에 들어올 수 있다. 그때 무턱대고 `mem::take` 하면
**두 번째 자리가 빈 줄이 되어 데이터가 조용히 사라진다.**

`taken` 표로 첫 방문만 옮기고 나머지는 복사하게 했다. 리뷰가 독립적으로
**20만 개 랜덤 + 6,220 전수 케이스**로 옛 `clone` 판과 결과가 같음을 확인했고,
결정적으로 — **함정 버전(naive take)이 기존 494개 테스트를 전부 통과**한다는 것도
확인했다. 새로 추가한 전수 테스트만 잡아낸다.

## 3. 이번에 배운 것

### "느리다"의 원인은 대개 자기가 마지막으로 본 곳에 없다

같은 증상을 두 번 보고받았고 원인이 두 번 다 달랐다. 1차는 판정(문자열 → 바이트),
2차는 할당자. 두 번 다 **코드를 읽어 추측한 지점이 아니라 측정이 가리킨 지점**이
답이었다.

특히 2차에서, 나는 "자료구조를 갈아엎어야 한다"고 결론 내릴 뻔했다. 실제로는
**두 줄짜리 할당자 교체가 2.9배**였다.

### 사용자의 비교 대상이 진단 도구다

*"EmEditor는 0.3초인데"*가 없었으면 1.8초에서 멈췄을 것이다. 구체적인 비교
기준이 있으니 "얼마나 더 갈 수 있나"를 조사할 이유가 생겼고, 조사해 보니
**11배가 더 남아 있었다.**

### 유명한 자료구조가 항상 답은 아니다

"큰 텍스트 편집 = rope"는 널리 퍼진 통념이지만, **측정하니 11.5배 느렸다.**
벤치마크를 볼 때 **그 벤치가 재생하는 워크로드가 내 것과 같은지** 봐야 한다.
rope 벤치는 사람의 타이핑을, 우리는 문서 전체 재작성을 한다.

### 전수 테스트가 랜덤보다 낫다

이번에도 반복됐다. 차등 코퍼스에 `\r`이 없어서 Critical을 놓쳤다. 알파벳에
**해당 도메인이 특수 취급하는 문자**(csv라면 `"` `\r` `\n` 구분자)를 반드시
넣어야 한다.

### 한 줄 변경이 가장 위험할 수 있다

`.clone()` → `mem::take`는 한 줄이고 12.8배 이득이지만, 중복 인덱스에서
데이터를 조용히 지운다. 그리고 **기존 494개 테스트가 그걸 못 잡았다.**
"작은 변경이니 테스트가 이미 커버할 것"이라는 가정이 정확히 여기서 깨진다.

### 알려진 한계

- **검색어에 `k`/`K` + 대소문자 무시**면 여전히 느리다(~21초). 유니코드에서
  U+212A(켈빈 기호 `K`)가 ASCII `k`로 접히는 **유일한** 예외라, 정확성을 위해
  그 경우만 옛 경로로 돌린다
- **병목이 파일 열기(~910ms)로 옮겨갔다** — 이제 치환의 4배다. 줄이려면 조사가
  보류한 플랫 버퍼 작업이 필요하다(자료구조 마이그레이션)
- `replace_all`이 UI 스레드에서 64스레드를 동기로 쓴다. 이 규모에선 괜찮지만
  진행률/취소를 붙이려면 별도 스레드로 빼야 한다
- `op_bytes`가 `String`의 여유 용량을 세지 않아 512MB 예산은 근사치다
  (최악 2배 과소평가 — 자릿수는 맞다)
- **Replace는 편집 모드에서만** 활성 (뷰 모드엔 편집 버퍼가 없다).
  지금은 왜 비활성인지 UI가 설명하지 않는다 — 개선 여지
- 앞선 문서의 한계(UTF-16 Whole cell 폴백, 따옴표 많은 CSV, 부분 인덱싱 중 찾기,
  Page Down 길게 누르기)는 그대로
