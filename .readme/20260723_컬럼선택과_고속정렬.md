# 컬럼 선택 + 고속 정렬 (indirect pointer sort)

- 날짜: 2026-07-23
- 목적: 헤더 클릭 컬럼 선택 + 컬럼값 기준 정렬(문자/숫자) 구현 및 대용량 정렬 최적화 정리

## 한 줄 요약

헤더 클릭으로 컬럼을 선택하고 그 컬럼 값 기준(문자/숫자 × 오름/내림)으로 **전체
파일을 정렬**한다. 행 바이트를 옮기지 않고 permutation만 만드는 **indirect pointer
sort**. 초기 구현이 10GB에 1분+ 걸리던 것을 단계적 최적화로 **10.8GB/3억행 5.9초,
898MB/1540만행 0.4초**(실측)까지 끌어올림. master 로컬 머지 완료, 테스트 69/69,
빌드 경고 0.

---

## 기능 (사용자 요청)

1. 컬럼 헤더 클릭 → 컬럼 전체 선택 (헤더 칸 아무 곳이나, 재클릭 해제)
2. 선택 상태에서 상단 툴바로 정렬: **문자↑ / 문자↓ / 숫자↑ / 숫자↓**
3. 선택 컬럼에 밝은 파랑 음영(헤더 진한 파랑 + 데이터 셀 세로 반투명)
4. 정렬 진행률 바(대용량 정렬 중 UI 프리징 없음)

## 핵심 접근: indirect pointer sort (permutation)

행 바이트를 절대 옮기지 않는다. `(정렬 키, 원본 행번호)` 쌍만 뽑아 정렬해
**행번호 permutation(Vec<u32>)**을 만들고, 뷰어는 `보이는 행 → permutation[i] →
원본 행번호 → 기존 line_range()`로 렌더한다. 기존 렌더 경로에 인덱싱 한 겹만
얹는 국소 변경. mmap 읽기 전용 모델 유지, 행 재작성 없음.

- 조사 근거: EMEditor가 15.2GB/1억행을 7.3초에 정렬 = 행 재작성 물리적 불가 →
  키만 뽑아 pointer/permutation 정렬이라는 강한 방증.
- 범위 = 옵션 A(in-memory par_sort). RAM 절약에 과하게 매달리지 않음(EMEditor도
  정렬 시 행 수 비례 메모리 사용). 우리는 mmap이라 파일 자체는 RAM에 안 올려 유리.

설계 스펙: docs/superpowers/specs/2026-07-23-column-sort-design.md

## 성능 최적화 여정 (실측, 대용량 실파일 기준)

측정 기준: 파일 A(898MB, 1540만행, 맨우측 숫자컬럼) / 파일 B
(10.8GB, 3억행, 맨우측 숫자컬럼).

| 단계 | 파일 A | 파일 B(10GB) | 핵심 변경 |
|---|---|---|---|
| 초기(String 방식) | — | **1분+** | split_fields로 전 컬럼 String 할당 + String 키 정렬 |
| ① 정수 키 | 0.65초 | 15.8초 | field_slice로 byte 슬라이스만, u128 pack 키, par_sort |
| ② 키 축소 | 0.55초 | 14.3초 | u128→u64(정렬 배열 절반) |
| ③ 락 제거+순차 | **0.4초** | **5.9초** | snapshot + par_chunks_mut 순차 순회 |

### 결정적 병목 = 키 추출의 RwLock (③)
10GB에서 단계 분리 측정: **키추출 10.3초 + 정렬 2.3초**. 정렬은 이미 빨랐고
키추출이 82%. 원인 = 행마다 `line_range()`가 `RwLock<Vec<u64>>` read-lock을
**3억 번** 획득 + rayon이 행을 랜덤 순서로 처리해 mmap 접근 흩어짐.

해결:
- `LineIndex.offsets`를 `RwLock<Arc<Vec<u64>>>`로 바꿔 `snapshot()`이 O(1) Arc
  clone. 워커는 락 없는 슬라이스를 공유.
- `par_chunks_mut(64K)`로 결과 배열을 큰 청크로 나눠 각 워커가 자기 구간을
  **순차** 순회 → mmap 순차 접근(prefetch 친화).
- 결과: **키추출 10.3초 → 1.5초 (7배)**.

### 정렬 키 인코딩 (사용자 아이디어 반영)
"String 쓰지 말고 raw 값 직접 비교, 바이트/자릿수 비교" 통찰을 그대로 구현:
- **문자**: 필드 앞 8바이트를 big-endian u64로 pack. big-endian이라 정수 대소 =
  바이트 사전식 순서(`ab < abc < b`). 짧은 필드는 0 패딩.
- **숫자**: f64를 정렬가능 u64로(부호비트 트릭 — 양수는 최상위비트 세우고 음수는
  전 비트 반전). 비수치/빈값은 u64::MAX(맨 뒤).
- **tie-break 최소화**: `truncated` 플래그(필드가 8B 초과 여부). 8B 이하면 키
  동률 = 완전 동일이라 원본 재접근 생략. 8B 초과 동률만 원본 전체 비교(정확성).
  → 값이 자주 겹치는 컬럼(도시명/카테고리 등)에서 재접근 폭발 방지.
  (초기엔 이 플래그가 없어 문자 정렬이 21초까지 튀는 버그를 벤치로 발견·수정.)

### SIMD 관련
키추출의 개행/구분자 탐색엔 이미 memchr(SIMD) 사용. **비교 기반 정렬 자체는
분기·랜덤 접근이라 SIMD 부적합** → 키 배열 축소로 캐시 효율을 올리는 게 정답
(radix sort는 숫자 전용·고난도라 보류).

## 아키텍처

### 신설: src/sort.rs
- `SortKind{Text,Number}`, `SortDir{Asc,Desc}`, `SortKey`(내부 정수 키 u64).
- `extract_and_sort(...)`: snapshot + par_chunks_mut 키추출 → par_sort_unstable →
  permutation. progress 콜백 지원.
- `spawn_sort(...)` + `SortJob`: 백그라운드 스레드 + AtomicU64 진행률. UI가 폴링해
  progress bar 그리고 완료 시 결과 수거.
- `extract_key_fast` / `full_field_fast`: 락 없는 hot path(offsets 슬라이스 +
  mmap bytes 직접).

### 수정
- src/index.rs: `offsets: RwLock<Arc<Vec<u64>>>`, `snapshot()`, 락 없는 `range_in()`.
- src/parse.rs: `field_slice()`(N번째 필드 byte 범위, 할당 없음, 따옴표 무시).
- src/app.rs: Document에 `selected_col`/`sort`/`sort_job`. 헤더 칸 전체 클릭 선택
  (ui.interact + rect 전체), 선택 컬럼 파랑 음영(헤더 불투명 + 데이터 반투명),
  툴바 정렬 컨트롤(Complete일 때만), 정렬 무효화(구분자/인코딩/헤더 변경·재인덱싱).

## 정책 / 엣지
- 정렬은 인덱싱 완료(Phase::Complete)에서만.
- 비수치(숫자 정렬)/빈값/컬럼 없음 → 방향 무관 맨 뒤.
- 안정 정렬(키 동률 시 원본 행번호 순).
- 헤더 행은 정렬에서 제외, 맨 위 고정.
- 텍스트 모드(구분자 None)에선 컬럼/정렬 UI 비활성.
- UTF-16은 구분자 2바이트라 field_slice(단일바이트 전용) 대신 디코딩 폴백.
