# Ctrl+휠 확대 범위와 탭 표시 — 계산을 믿다가 두 번 틀린 기록

**작업 범위:** `9f7e0f8..92009f5` (4 커밋, 브랜치 `feat/hex-mode`)
**날짜:** 2026-08-03

요구는 둘이었다. "Ctrl+휠로 확대하면 메뉴랑 상태바까지 커지는데, 에디터 글씨만
커졌으면 좋겠다." 그리고 "탭으로 뗀 칸에 배경색을 다르게 줄 수 있냐."

첫 번째는 한 번에 됐다. 두 번째는 **세 커밋이 걸렸다** — 기능은 첫 커밋에서
완성됐는데 색이 안 보여서 두 번을 더 고쳤다. 이 문서의 대부분은 그 두 번에 대한
것이다.

| 커밋 | 내용 |
|---|---|
| `cd58894` | Ctrl+휠 확대를 데이터 영역으로 한정 — 크롬은 고정 |
| `ec2f8f9` | 탭 칸에 옅은 배경 (알파 28) |
| `91ef0f2` | 알파 28 → 56 (여전히 안 보임) |
| `92009f5` | 알파 56 → 120 (실제로 보이는 값) |

---

## 1. 확대 범위를 가르는 것은 `TextStyle` 하나

기존 구현은 `ctx.set_zoom_factor`로 **창 전체**를 확대했다. 그래서 본문 글자를
키우면 메뉴·툴바·상태바가 함께 커졌고, 큰 배율에서는 정작 본문에 남는 자리가
줄었다.

배율을 전역이 아니라 `App::view_scale`로 들고 데이터 영역에만 곱하는 것으로
바꿨다. `zoom_factor`는 손대지 않으므로 OS DPI 스케일링은 egui가 하던 대로 한다.

크롬이 고정되는 근거는 이미 코드 안에 있었다. `theme.rs`가 데이터 영역은
`Body`/`Monospace`로, 크롬은 `Button`으로 그리도록 갈라 두었다(`chrome_text`).
확대를 앞의 둘에만 얹으면 뒤는 저절로 고정된다. 새 구조를 만든 게 아니라 이미
있던 경계를 쓴 것이다.

**행 높이도 같은 배율로 함께 키운다.** 글자만 키우면 큰 배율에서 글자가 행 밖으로
삐져나가 잘리고, 행만 키우면 사이가 허옇게 뜬다. 그래서 `ROW_HEIGHT`/`MONO_SIZE`
상수를 `theme::row_height(scale)` / `mono_size(scale)` 함수로 바꾸고, 렌더는
`doc_row_height`/`doc_font_id`를 거치게 했다. 상수 직접 참조는 `#[cfg(test)]`로
테스트에만 남겼다 — 프로덕션에서 상수를 쓰면 배율을 안 타는 자리가 조용히 생긴다.

배율은 `App`이 소유하고 `Document`가 사본을 든다. 세 렌더 함수가 `&mut Document`만
받고 `&App`은 못 받아서(빌림 충돌), 인자를 더하면 호출부와 테스트가 전부 시그니처를
바꿔야 한다. 문서는 이미 `visible_rows`처럼 프레임 상태를 담는 자리다.

## 2. 탭 폭은 탭스톱이 아니다

탭 칸을 칠하려면 그 칸이 어디서 어디까지인지 알아야 한다. "다음 탭스톱까지"라면
앞 글자들의 폭에 따라 달라지므로 계산이 복잡해진다.

그런데 epaint는 탭을 **고정폭 빈 글자**로 그린다
(`TAB_SIZE(4) × 스페이스 advance`, `epaint-0.28.1/src/text/font.rs:187-190`).
갤리 안에서 탭은 평범한 한 글자이고, 칠할 구간은 `x_of(i)..x_of(i+1)`이다.
헥스 정렬을 고칠 때 배운 규율 그대로 — 산술로 추정하지 않고 갤리에게 묻는다.

`render_text`에는 줄을 그리는 경로가 셋(뷰, 뷰+검색중, 편집)이라 셋 다 칠했다.
뷰 경로가 까다로웠는데, 그 자리 주석이 "여기서 galley를 따로 만들어 재면 Label의
레이아웃과 어긋날 수 있다"고 경고하고 있었다. `Label::layout_in_ui`가 **Label
자신의 galley**를 돌려주면서 그리지는 않는다는 것을 확인하고, 그 galley로 좌표를
얻어 배경 → 글자 순으로 그렸다.

## 3. 두 번 틀린 색 — 이 세션의 본론

기능은 `ec2f8f9`에서 완성됐다. 테스트 7건이 통과했다. 그런데 화면에는 아무것도
없었다.

### 왜 안 보였나

알파를 28로 뒀다. 순백 위에서 rgb(240,242,246) — 흰색과 10단계 남짓이다.
줄무늬(`stripe_bg`, gray 250)와 구분도 안 되는 수준이었다.

56으로 올렸다. 여전히 "차이가 있는 것 같은데 눈으로 도저히 구분이 안 가는"
상태였다. 실제 색은 rgb(233,235,240)으로, **격자선(gray 216)보다도 옅었다.**

120에서야 rgb(204,210,222)가 되어 보였다.

### 두 번 다 같은 원인

**머릿속 산술을 믿었다.** `out = fg×a + bg×(1-a)`로 계산해서 "알파 56이면
rgb(223,229,237)쯤 되겠지"라고 판단했다. 실제 값은 rgb(233,235,240)이었다.

`Color32`는 채널을 **감마 공간에서 미리 곱해** 들고 있다
(`ecolor-0.28.1/src/color32.rs:97-113`). `from_rgba_unmultiplied(110,135,175,56)`
의 `.r()`은 110도, 단순 곱셈값 24도 아닌 **52**다. GPU 합성도 선형 공간에서
일어난다. 단순 비례 계산과 결과가 다르고, 그 차이가 정확히 "보인다/안 보인다"를
갈랐다.

`91ef0f2` 커밋 주석에 적어 둔 "약 rgb(223,229,237)"도 틀린 값이다.

### 테스트는 왜 못 잡았나

모양 개수를 세는 테스트 7건이 전부 통과하는 동안 화면에는 아무것도 없었다.
사각형은 정상적으로 그려지고 있었기 때문이다. **그려지는 것과 보이는 것은
다른 문제다.**

색 검사는 `알파 > 0`만 봤다. 0이 아니면서 안 보이는 값이 얼마든지 있다.

하한을 두는 테스트를 쓰려고 합성 픽셀을 계산했다가 **또 틀렸다.** 감마 premultiply를
모르는 상태로 쓴 식이라, 현재 색에서도 실패하고 옛 색에서도 실패하는(부호가 뒤집힌)
무의미한 테스트가 나왔다. 결국 합성 계산을 포기하고 사람이 실제로 조절하는 값인
**입력 알파**에 하한(100)을 뒀다. 근거는 계산이 아니라 화면이다.

### 곁가지로 드러난 틀린 테스트

알파를 120으로 올리자 `tab_bg_is_fainter_than_find_shades`가 실패했다.
확인해 보니 **그 테스트가 틀린 것이었다.** "탭 알파 < 찾기 알파"를 요구했는데,
매치는 탭 **뒤에** 그려지므로 알파 크기는 기준이 아니다. 실제 요구는 "겹쳤을 때
구분되는가"이고, 탭 위 매치는 rgb(192,189,217)로 탭(204,210,222)과 색조가
뚜렷이 갈린다. 색조 관계(탭=청회색, 찾기=보라)를 보는 테스트로 바꿨다.

## 4. 배선을 테스트하지 않으면 함수만 완벽해진다

탭 기능에서 변이 테스트로 세 건이 살아남았고, 그중 하나가 뼈아팠다.

처음엔 좌표 산술을 테스트에서 다시 계산하는 방식으로 짰다. 그래서 **렌더가
`paint_tab_shades`를 아예 호출하지 않아도 전부 통과**했다. 함수는 완벽히
테스트했는데 배선은 하나도 안 본 상태였다.

실제 문서를 그려서 탭 색 사각형 개수를 세는 테스트로 바꿨다. 이제 세 경로 중
하나만 호출을 지워도 실패한다. 나머지 둘(byte/char 인덱스, off-by-one)도 막았다.

확대 쪽에서도 하나 살아남았다. 배율만 바꾸고 `install_text_styles` 재적용을 빼도
통과했다 — `Label`로 그리는 셀은 `TextStyle::Body`를 타므로 재적용이 없으면 행만
커지고 글자는 그대로 남는 실제 결함이다.

## 검증

- 744 테스트 통과 (736 → 744, 확대 6건 + 탭 8건 추가)
- clippy 20 (변화 없음)
- 릴리즈 빌드 성공
- 변이 테스트: 확대 4건, 탭 5건 — 처음 살아남은 4건 전부 봉합

## 배운 것

1. **그려지는 것과 보이는 것은 다르다.** 모양 개수를 세는 테스트는 색이 투명에
   가까워도 통과한다. 시각 요소는 "나왔는가"와 "보이는가"를 따로 물어야 한다.

2. **색 합성을 손으로 계산하지 말 것.** `Color32`는 감마 공간 premultiplied이고
   GPU 합성은 선형 공간이다. 두 번 틀렸고, 두 번째는 그 실수를 잡으려던 테스트
   안에서 또 틀렸다. 라이브러리 내부를 재현하는 테스트는 그 자체가 버그의 자리다.

3. **테스트가 실패했을 때 코드가 아니라 테스트가 틀렸을 수 있다.**
   `tab_bg_is_fainter_than_find_shades`가 그랬다. 알파 크기는 애초에 기준이
   아니었는데, 첫 구현에서 우연히 만족돼 통과하고 있었을 뿐이다.

4. **사용자의 "안 보인다"가 가장 빠른 진단이었다.** 테스트 7건, 변이 3건을
   돌리는 동안 못 잡은 것을 한 문장이 잡았다. 특히 "빈 파일 열면 edit mode에
   plain text인데 탭 간격만 떼고 색은 안 보인다"는 보고는 재현 조건까지 담고
   있어서 그대로 태울 수 있었다.

5. **이미 있는 경계를 쓰면 새 구조가 필요 없다.** 확대 범위를 가른 것은
   `Body`/`Button` 분리 하나였고, 그건 크롬 폰트를 정리할 때 이미 그어 둔
   선이었다.

## 다음

- 탭 배경 농도는 화면에서 다시 조정할 수 있다(`theme::tab_bg`의 알파).
  하한 100은 테스트가 지킨다.
- 확대 배율은 세션 간 저장되지 않는다 — 껐다 켜면 1.0으로 돌아간다.
- 표 모드(CSV/TSV)에는 탭 배경이 없다. 거기서 탭은 구분자라 문자로 남지 않는다.
- 다크 테마를 넣는다면 `tab_bg`는 순백 전제라 다시 잡아야 한다.
