# 구분자 변환 (Convert Delimiter)

**작업 범위:** `444822b..b3686dd` (3 커밋)
**날짜:** 2026-07-25

세퍼레이터로 파싱된 상태에서 구분자를 바꾸는 기능. 콤마/탭/파이프/세미콜론과
임의의 ASCII 커스텀 구분자 사이를 **어느 방향으로든** 변환한다.

---

## 1. 기존 기능과 무엇이 다른가

툴바에 이미 `Delimiter` 드롭다운이 있었다. 그래서 처음엔 "이미 있는 기능
아닌가?" 싶었지만, 둘은 하는 일이 다르다.

| | 툴바 `Delimiter` 드롭다운 | `Tools > Convert Delimiter…` |
|---|---|---|
| 하는 일 | 바이트를 컬럼으로 나누는 **기준** | **바이트 자체**를 재작성 |
| 파일 변경 | 없음 | 있음 (dirty, 저장 필요) |
| 되돌리기 | 드롭다운을 되돌리면 끝 | Ctrl+Z 한 번 |

툴바 쪽은 **보기 설정**이다. 콤마 파일에서 구분자를 탭으로 바꾸면 표가 한
컬럼으로 무너질 뿐, 파일 안에는 여전히 콤마가 있다.

이 구분이 흐려지면 "탭으로 바꿨는데 왜 파일에 아직 콤마가 있지?"로 직결되므로,
다이얼로그 본문에 **"파일 내용이 바뀝니다"** 를 명시하고 상태 필드도 툴바와
완전히 분리했다(`convert_target` / `convert_custom_input`). 한쪽을 만지다
다른 쪽이 따라 움직이면 데이터를 의도치 않게 바꾸는 사고가 된다.

---

## 2. 왜 Replace All 로는 안 되는가

작업 중 나온 질문: *"사실 replace all 하고 같은 거라 쉬운 기능 아닌가?
게다가 한 문자니까 찾기도 쉽고."*

맞는 직관인데 한 군데가 다르다. **인용부호가 두 방향 모두에서 규칙을 깬다.**

### 방향 1 — 인용 안의 구분자를 건드리면 안 된다

```
입력 (콤마 구분, 3필드):  홍길동,"서울, 강남구",30
바이트 치환 → 탭:          홍길동→"서울→ 강남구"→30     ❌ 4필드로 깨짐
올바른 변환 →              홍길동→서울, 강남구→30        ✅ 3필드 유지
```

인용 안의 콤마는 구분자가 아니라 **데이터**다.

### 방향 2 — 새 구분자가 값에 있으면 없던 인용을 만들어야 한다

```
입력 (탭 구분, 2필드):    홍길동→서울, 강남구
바이트 치환 → 콤마:        홍길동,서울, 강남구           ❌ 다시 읽으면 3필드
올바른 변환 →              홍길동,"서울, 강남구"          ✅ 2필드 유지
```

치환은 없던 인용부호를 **만들어내지 못한다**.

그래서 파싱이 필요하다. 값에 새 구분자가 있는 셀이 하나도 없고 인용부호도 전혀
없는 파일이라면 정말로 Replace All 과 같지만, 그 조건을 사용자가 미리 알 수
없으니 코드가 판단해야 한다.

---

## 3. 빠른 경로

전 행에 `split_fields`를 부르면 행당 필드 수만큼 `String`을 할당한다. Task M
에서 이 비용이 1,542만 행에서 판정만으로 17.6초였다.

**인용부호도 새 구분자 바이트도 없는 행**은 위 두 함정이 **둘 다 성립하지
않는다.** 그때는 `old` 바이트를 `new`로 갈아 끼우는 것으로 충분하다.

### 조건이 완전한 근거

`join_fields`가 인용을 씌우는 조건은 값에 `new` / `"` / `\n` / `\r` 중 하나라도
있을 때다.

- `new`, `"` → 위 조건이 **직접** 배제
- `\n`, `\r` → **`EditBuffer.lines[i]`가 개행을 담지 않는다**는 이 코드베이스의
  불변식이 배제 (줄바꿈은 저장할 때 붙는다)

넷이 전부 막히므로, 빠른 경로를 탄 행은 인용이 전혀 필요 없고 결과가 폴백과
비트 단위로 같다.

이 규율은 찾기의 바이트 판정과 같다 — **바이트 경로는 "확정" 아니면 "폴백"만
결론지을 수 있고, 절대 "아님"을 결론짓지 않는다.** 애매하면 폴백이 정답이다.
폴백은 느릴 뿐 틀리지 않는다.

## 4. 성능

실사용 TSV (15,426,933행 / 857MB), 탭 → 콤마:

| | |
|---|---|
| **convert_all (rayon 병렬)** | **210 ms** |
| 전 행 파싱 재조립(빠른 경로 없이) 환산 | 5,421 ms |

빠른 경로가 이 파일에서 **100%** 먹혔다(인용부호가 없는 TSV).

### 빠른 답이 틀린 답은 아닌가

속도만 보고 끝내면 안 되므로 **실파일 1,542만 행 전부**를 파싱 재조립 결과와
대조했다.

```
전 행 차등 검증: 15,426,933 행 중 불일치 0
왕복 검증(200만행): 필드 값 불일치 0
```

벤치는 앱의 실제 `parse.rs` / `convert.rs`를 그대로 복사해 돌렸다(재구현 아님).

## 5. 걸린 것 — 커버리지 검사가 자기 자신을 속였다

빠른 경로가 통째로 죽어 있어도(항상 폴백) 차등 테스트는 통과한다. 결과가
같으니까. 그래서 "빠른 경로를 탄 입력이 0이면 실패" 검사를 넣어 뒀는데 —

**그 검사가 작동하지 않았다.** 진짜 조건을 `if false`로 바꿔도 통과했다.

```rust
// 문제의 코드 — 테스트가 판정식을 자기편에서 다시 계산한다
fn took_fast_path(line: &str, new: u8) -> bool {
    memchr::memchr2(b'"', new, line.as_bytes()).is_none()
}
```

이건 판정식의 **복사본**이라, 프로덕션의 진짜 조건을 지워도 자기 사본만 보고
계속 "빠른 경로를 탔다"고 센다.

고친 방법은 관찰을 **실행 결과로** 받는 것:

```rust
pub enum ConvertPath { Fast, Fallback }
pub fn convert_line_traced(line: &str, old: u8, new: u8) -> (String, ConvertPath);
```

이제 경로를 프로덕션 코드가 직접 보고한다. `if false` 변이를 넣으면 테스트가
**실패한다**.

이 코드베이스에서 **다섯 번째** 반복된 같은 결함이다(테스트가 가드를 복사해
인라인으로 적어 두면 진짜 가드를 지워도 통과). 이번엔 규율로 막지 않고 구조로
막았다 — 복사할 수 있는 판정식을 아예 노출하지 않는다.

## 6. 커스텀 구분자를 ASCII 로 제한한 이유

`join_fields`가 `delim as char`로 비교하고 `out.push(delim_ch)`로 쓴다
(`parse.rs:298`). 비ASCII 바이트 `0xA9`를 넘기면 `as char`가 U+00A9 `©`가 되어
UTF-8로 **두 바이트**가 쓰이는데, 파서는 한 바이트를 기대한다. 파일이 깨진다.

다이얼로그가 막고, 조용히 비활성화하는 대신 화면에 이유를 표시한다.

**관련해서 기존 툴바에도 같은 뿌리의 문제가 있다** — `app.rs:985`가
`as_bytes().first()`로 **첫 바이트**를 취하므로 `£`를 입력하면 `0xC2`(UTF-8
선행 바이트)가 구분자가 된다. 다만 그건 **보기 전용이라 데이터를 깨뜨리지
않으므로** 이번 범위에 넣지 않고 별도 항목으로 남겼다.

## 7. undo / 상태 처리

`replace_all_in_doc`과 같은 규율:

- 실제로 **달라진 행만** `EditOp::Replace` **하나**에 모아 Ctrl+Z 한 번에 전부 복구
- `mem::replace`로 옛 String을 그대로 가져가 문자열 복사 0
- 바뀐 행이 없으면 undo에 담지 않고 dirty도 세우지 않는다(유령 단계 방지)

변환 후:

- `doc.sep`을 새 구분자로 **맞춘다** — 안 맞추면 표가 한 컬럼으로 무너진다
- 컬럼에 매인 상태(정렬·선택·하이라이트)는 **버린다** — 컬럼 경계가 달라졌다
- `has_header`는 **유지한다** — 변환은 행 수도 필드 수도 바꾸지 않으므로 헤더
  행은 그대로 헤더다. 지우면 0번 행이 데이터로 내려와 정렬·추출이 헤더를
  데이터처럼 다룬다

**뷰 모드에서 눌러도 편집 모드로 자동 전환한다.** Replace가 편집 전용이라
막히는 것을 사용자가 불편해했으므로 같은 벽을 만들지 않는다.

## 8. 검증

`cargo test` **518 passed / 0 failed / 4 ignored**, clippy 새 경고 0,
release 빌드 완료.

가드를 **변이 테스트**로 확인했다 — 지우면 테스트가 실패한다
(실패 건수는 `cargo test convert` 기준):

| 변이 | 결과 |
|---|---|
| `convert_enabled`을 항상 true 로 | 3건 실패 |
| `convert_enabled`의 텍스트 모드·no-target 가드 제거 | 2건 실패 |
| 빠른 경로 조건 제거(항상 빠른 경로) | 6건 실패 |
| 빠른 경로를 죽임(항상 폴백) | 커버리지 검사 실패 |
| `has_header`를 다른 컬럼 상태처럼 초기화 | 1건 실패 |
| no-op 조기 반환 제거 | 1건 실패 |

차등 테스트는 알파벳 `{a, ", ,, \t, |}` 길이 0~4 **전수** × 구분자 쌍 교차.
랜덤이 아니라 전수인 이유는 이 코드베이스에서 랜덤 79.7만 건이 놓친 따옴표
위음성을 전수 프로브가 잡은 적이 있기 때문이다.

## 배운 것

**"이미 있는 기능"처럼 보이는 요청이 실은 다른 기능일 수 있다.** 툴바에 구분자
드롭다운이 있어서 처음엔 중복 요청으로 보였다. 실제로는 "보는 방식"과 "저장되는
데이터"라는 다른 축이었고, 그 둘을 UI에서 명시적으로 갈라 놓는 것이 기능의
절반이었다.

**"쉬운 기능 아닌가"라는 직관은 대개 맞고, 틀리는 지점이 정확히 한 곳이다.**
구분자 변환은 정말로 Replace All 과 90% 같다. 다른 10%가 인용부호였고, 그것이
데이터를 조용히 깨뜨리는 부분이었다.

**테스트가 자기 자신을 속이는 방식은 반복된다.** 판정식을 테스트가 다시 계산하면
가드가 죽어도 통과한다. 이 브랜치에서만 다섯 번 나왔다. 규율("복사하지 말자")로는
못 막았고, 구조(복사할 판정식을 노출하지 않기)로 바꾼 뒤에야 막혔다.

**빠른 경로가 100% 먹히는 파일에서는 폴백을 테스트만이 검증한다.** 실파일에서
폴백이 한 번도 안 돌았으므로, 그 경로의 정확성은 전수 코퍼스 테스트가 유일한
근거다.
