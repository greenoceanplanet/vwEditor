# 병렬 인덱싱 설계

> vwEditor의 개행 offset 인덱싱을 단일 스레드 순차 스캔에서 rayon 기반 N-way 병렬 스캔으로 교체한다.

**작성일:** 2026-07-22
**목표:** EMEditor처럼 사용자의 모든 코어를 활용해 대용량 파일(7GB~40GB)을 수 초 내 인덱싱한다.

---

## 배경 / 문제

현재 `spawn_indexer`는 백그라운드 스레드 **하나**로 파일을 8MB 청크씩 처음부터 끝까지 순차 스캔하며 개행 offset을 찾는다. 7GB 파일이면 코어 하나가 7GB를 전부 훑어야 하므로 인덱싱이 느리다. EMEditor는 모든 코어가 파일을 구간별로 나눠 동시에 스캔해 7GB를 0.7초에 연다.

개행 스캔은 **완벽히 병렬화 가능한(embarrassingly parallel)** 작업이다: 파일을 구간으로 나눠 각 구간에서 독립적으로 개행을 찾은 뒤, 구간 순서대로 결과를 이어붙이면 순차 스캔과 동일한 offset 배열이 나온다.

## 결정 사항 (확정)

- **병렬화 방식:** 전체 즉시 병렬 스캔 — 파일을 코어 수만큼 구간으로 분할해 rayon으로 동시 스캔
- **라이브러리:** rayon
- **프라이밍 유지:** 첫 화면 즉시성을 위해 명시적 프라이밍 단계를 분리 (아래 상태 머신 참조)
- **중단 유지:** 40GB 같은 초대형 파일은 중단이 실제로 필요
- **재개 = 처음부터 재스캔:** 병렬에서 중간 재개는 복잡하므로, "이어서 읽기"는 인덱스를 클리어하고 처음부터 다시 병렬 스캔한다
- **중단 시 보이는 범위:** 맨 앞부터 **연속으로 완료된 부분까지** 보여준다 (구멍 없는 prefix)

## 아키텍처

### 3단계 상태 머신

기존 `Phase` enum(`Priming`/`Indexing`/`Paused`/`Complete`)을 유지하되 의미를 명확히 한다.

```
파일 열기
   │
   ▼
[Priming]  ── 맨 앞 PRIME_BYTES(수백 행분)를 단일 스레드로 즉시 순차 스캔
   │           → 첫 화면 표시 (수 ms)
   ▼
[Indexing] ── 파일 전체를 rayon으로 N-way 병렬 스캔
   │           ├─ 정상 완주 ──────────────► [Complete]
   │           └─ 중단 요청 감지 ──────────► [Paused] (연속 prefix까지 병합)
   ▼
[Paused]
   └─ "이어서 읽기" → 인덱스 클리어 → [Priming]부터 다시
```

**핵심:** 프라이밍은 반드시 병렬 스캔 **전에** 완료되어 맨 앞 행이 먼저 인덱스에 들어간다. 병렬 스캔은 파일 여기저기를 동시에 채우므로, 프라이밍 없이는 뒷부분 offset이 앞부분보다 먼저 들어와 첫 화면이 늦어질 수 있다.

### 구간 분할과 경계 규칙

파일 전체 `[0, total)`을 워커 수 `W = available_parallelism()`개의 구간으로 균등 분할한다.

```
구간 k: [start_k, end_k)   where start_k = k * total / W,  end_k = (k+1) * total / W
```

각 구간 경계는 **바이트 위치로만** 자른다(줄 중간이어도 무방). 각 워커는 자기 구간에서 다음 규칙으로 로컬 `Vec<u64>`를 만든다:

- **줄 시작 = 개행 바로 다음 위치.** 워커 k는 `[start_k, end_k)` 범위에서 개행 패턴을 찾아, **개행 다음 위치(next)가 `< total`이면** 그 절대 offset을 로컬 Vec에 push한다.
- **첫 줄 시작(0)은 구간 0만** push한다 (파일 맨 처음).
- 워커는 자기 구간 시작 직전의 개행은 담당하지 않는다 — 그 개행의 "다음 위치"는 이웃 구간이 담당하거나, 정확히 자기 start이면 자기가 담당한다. **규칙 통일:** 개행 다음 위치가 `[start_k, end_k)` 안에 들어오는 개행만 담당 → 각 offset은 정확히 한 워커만 push (중복 없음, 누락 없음).
- **멀티바이트 개행 경계:** UTF-16(step=2)에서 개행 패턴이 `end_k` 직전에 걸쳐 있을 수 있으므로, 스캔 슬라이스는 `end_k`를 `step-1`만큼 내다본(peek) `scan_end`까지 잡는다. 단 "다음 위치가 자기 구간 담당인지"는 여전히 `[start_k, end_k)` 기준으로 판정한다. (기존 `index_range`의 peek 로직 재사용)

이 규칙이면 **구간 0, 1, …, W-1의 로컬 Vec을 인덱스 순서대로 concat한 결과 = 순차 `scan_offsets`(정답지)** 이 정확히 성립한다.

> **경계 상세 (담당 규칙의 형식화)**
> 워커 k는 자기 슬라이스 `bytes[start_k .. scan_end]`에서 개행 패턴을 찾되, **매치 시작 위치의 절대값이 `[start_k, end_k)` 안**일 때만 그 개행을 처리한다. 처리 시 `next_abs = 매치시작 + step`을 계산하고, `next_abs < total`이면 push. `start_k`(=0 아닌 구간 시작)에 걸친 이전 줄은 이웃 구간(k-1)이 그 개행을 처리해 `next_abs = start_k`를 push하므로, 구간 k가 다시 push하지 않는다. → 정확히 한 번.

### 병합 (정상 완주 + 중단 통일)

정상 완주와 중단을 **하나의 병합 로직**으로 처리한다:

- 각 워커는 자기 구간을 **왼쪽→오른쪽** 순서로 스캔하며 로컬 Vec을 채우고, 자기 구간 완료 여부(`done: bool`)와 완료한 바이트 위치(`progress: usize`)를 기록한다.
- 병합 시 구간 0부터 순서대로:
  - 구간이 **완전히 완료**되었으면 그 로컬 Vec 전체를 이어붙인다.
  - 첫 번째 **미완료** 구간을 만나면, 그 구간이 그때까지 스캔한 부분(로컬 Vec)까지만 이어붙이고 **멈춘다** (그 뒤 구간들은 앞이 비어 연속성이 깨지므로 버림).
- **정상 완주:** 모든 구간이 완료 → 전체 concat = 완전한 인덱스.
- **중단:** 맨 앞부터 연속 완료된 prefix까지만 → 구멍 없는 연속 행이 보인다.

이 통일 규칙 덕에 병합 코드는 "구간 0부터 훑다가 첫 미완료에서 멈춤" 한 줄로 표현된다.

## 파일 구조

### 수정: `src/indexer.rs`

- `newline_pattern`, `scan_offsets`, `index_range`(단일 구간 스캔의 핵심 루프)는 **그대로 유지** — 병렬 워커가 자기 구간을 스캔할 때 재사용한다. `index_range`가 `chunk_size`/`pos`/`should_pause`/`on_chunk_done`을 파라미터로 받는 현재 시그니처가 병렬화에 그대로 맞는다.
- **`scan_segment` 신설:** 한 구간 `[seg_start, seg_end)`를 스캔해 로컬 `Vec<u64>`와 `(done, progress)`를 반환하는 순수 함수. 내부적으로 `index_range`와 동일한 청크 루프를 쓰되, `LineIndex`에 직접 push하지 않고 로컬 Vec에 모은다. 중단 플래그를 청크마다 확인.
- **`prime` 신설:** 맨 앞 `PRIME_BYTES` 구간을 순차 스캔해 `LineIndex`에 즉시 채우는 함수 (첫 화면용). 첫 줄 시작(0) 포함.
- **`spawn_indexer` 재작성:** (1) `prime` 호출 → `Phase::Priming` → 첫 화면 표시, (2) `rayon`으로 전체 구간을 `par_iter` 스캔 → `Phase::Indexing`, (3) 결과 병합 → `Phase::Complete` 또는 `Phase::Paused`. 진행 표시는 각 워커의 `progress` 합산.

### 수정: `src/index.rs`

- **`bulk_extend(offsets: Vec<u64>)` 또는 `replace_offsets` 신설:** 병렬 병합 결과를 한 번의 락으로 `Vec`에 반영. 현재 `push_offset`(하나씩 락)은 병렬 결과 병합에 비효율적이므로, 병합된 전체 Vec을 한 번에 넣는 API를 추가한다. 프라이밍이 채운 앞부분과 병렬 결과의 관계 처리 방식은 아래 "프라이밍/병렬 인덱스 이음새" 참조.
- `Phase`, `IndexStatus`, `status`, pause 관련 API는 유지.

### 수정: `src/app.rs`

- `open_path`: `spawn_indexer` 호출부는 시그니처가 같으면 변경 최소. 프라이밍이 spawn 내부로 들어가므로 호출부는 그대로.
- 상태바: `Priming`/`Indexing`은 "인덱싱 중… N%", `Paused`는 "일시정지 — 이어서 읽기"(재스캔), `Complete`는 "완료 — N행". 진행률 계산은 기존 `bytes_done`/`total_bytes` 유지.

### 수정: `Cargo.toml`

- `rayon = "1"` 추가.

### 프라이밍 / 병렬 인덱스 이음새 (핵심 주의점)

프라이밍이 맨 앞 offset들을 `LineIndex`에 넣은 뒤, 병렬 스캔이 완료되면 병렬 결과(전체 파일의 완전한 offset 배열)로 **교체**한다. 프라이밍 결과는 병렬 결과의 앞부분과 정확히 일치하므로(같은 스캔 규칙), 병렬 완료 시 `replace_offsets(merged)`로 통째 교체하면 이음새 없이 이어진다. 병렬 스캔 진행 중에는 프라이밍 offset이 그대로 남아 첫 화면이 유지된다.

> **대안 검토:** 프라이밍 offset을 그대로 두고 병렬은 프라이밍 끝 이후만 스캔해 append하는 방식도 가능하나, 구간 경계와 프라이밍 경계가 얽혀 병합이 복잡해진다. **교체 방식**이 규칙이 단순하고(병렬은 항상 `[0,total)` 전체를 담당), 정답지(`scan_offsets`)와의 대조 테스트가 그대로 성립하므로 이를 채택한다.

## 에러 처리 / 엣지 케이스

- **빈 파일:** `total == 0` → 프라이밍/병렬 모두 no-op, 즉시 `Complete`, `line_count == 0`.
- **파일 < PRIME_BYTES:** 프라이밍이 전체를 스캔 → 이어지는 병렬 스캔은 `[0,total)`을 (작으므로 사실상 구간 1개로) 다시 훑어 같은 결과를 내고 교체한다(무해, 특별 분기 불필요).
- **워커 수 = 1 (단일 코어):** 구간 1개 → 순차와 동일하게 동작.
- **중단이 프라이밍 중에 눌림:** 프라이밍은 매우 짧으므로 프라이밍 완료 후 병렬 진입 직전 플래그 확인 → 병렬 생략하고 `Paused`.
- **멀티바이트 개행(UTF-16) 구간 경계 스트래들:** peek 로직으로 처리(기존 회귀 테스트 유지).

## 테스트 전략

기존 테스트(순차 `scan_offsets` 정답지, UTF-16 경계 회귀)는 **그대로 통과해야 한다** — 병렬 결과가 순차와 동일함을 보장하는 오라클이기 때문.

추가 테스트:

1. **`scan_segment`가 구간 경계에서 정확히 담당:** 여러 구간으로 나눈 결과를 concat하면 `scan_offsets` 전체 스캔과 일치 (UTF-8 LF).
2. **병렬 = 순차 동치 (UTF-8):** 여러 줄 파일을 `spawn_indexer`로 병렬 인덱싱한 결과 offset == `scan_offsets` 전체. 다양한 워커 수(1, 2, 4, 8)에서.
3. **병렬 = 순차 동치 (UTF-16LE), 멀티 청크:** 기존 `indexer_multi_chunk_utf16le_matches_scan_offsets`가 병렬 경로로도 통과.
4. **구간 경계가 개행에 정확히 걸침:** 개행 다음 위치가 정확히 `start_k`인 케이스에서 중복/누락 없음.
5. **중단 시 연속 prefix:** 중간 구간을 미완료로 강제(주입 가능한 pause)한 뒤, 병합 결과가 맨 앞부터 연속된 offset만 담고 구멍이 없는지.
6. **빈 파일 / 1줄 파일 / PRIME_BYTES 미만 파일** 엣지.

`scan_segment`와 병합 로직은 GUI/스레드 없이 순수 함수로 단위 테스트 가능하게 설계해, 병렬 동치성을 결정적으로 검증한다.

## 비목표 (YAGNI)

- SIMD/AVX512 개행 스캔 — 이번 범위 아님(리서치에서 보류 결정).
