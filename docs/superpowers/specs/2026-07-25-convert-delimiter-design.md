# 구분자 변환 (Convert Delimiter) 설계

**작성일:** 2026-07-25
**브랜치:** `feat/editing-and-save`

## 목표

파일의 데이터를 실제로 재작성해서 구분자를 바꾼다. 콤마/탭/파이프/세미콜론과
임의의 ASCII 커스텀 구분자 사이를 어느 방향으로든 변환한다.

## 배경 — 기존 기능과의 구분

툴바에 이미 `Delimiter` 드롭다운이 있다(`app.rs:967`). 그것은 **보기 설정**이다:
바이트를 어떻게 컬럼으로 나눌지를 정할 뿐 파일 바이트를 건드리지 않는다.

이 기능은 다르다. 두 역할이 섞이면 "탭으로 바꿨는데 왜 파일에 아직 콤마가
있지?"라는 혼란으로 직결되므로, 문구와 배치로 분명히 갈라 놓는다.

| | 툴바 `Delimiter` 드롭다운 | `Tools > Convert Delimiter…` |
|---|---|---|
| 하는 일 | 바이트를 컬럼으로 나누는 **기준** | **바이트 자체**를 재작성 |
| 파일 변경 | 없음 | 있음 (dirty, 저장 필요) |
| 되돌리기 | 드롭다운을 되돌리면 끝 | Ctrl+Z 한 번 |

## 왜 단순 바이트 치환이 아닌가

"구분자 한 글자를 다른 한 글자로" 이므로 Replace All과 같아 보이지만, 인용
부호가 두 방향 모두에서 규칙을 깬다.

**방향 1 — 인용 안의 구분자를 건드리면 안 된다.**

```
입력 (콤마 구분, 3필드):  홍길동,"서울, 강남구",30
바이트 치환 → 탭:          홍길동→"서울→ 강남구"→30     ❌ 4필드로 깨짐
올바른 변환 →              홍길동→서울, 강남구→30        ✅ 3필드 유지
```

인용 안의 콤마는 구분자가 아니라 데이터다. 바이트 치환은 그것을 구별하지
못한다.

**방향 2 — 새 구분자가 값에 있으면 인용을 새로 만들어야 한다.**

```
입력 (탭 구분, 2필드):    홍길동→서울, 강남구
바이트 치환 → 콤마:        홍길동,서울, 강남구           ❌ 다시 읽으면 3필드
올바른 변환 →              홍길동,"서울, 강남구"          ✅ 2필드 유지
```

치환은 없던 인용부호를 만들어내지 못한다.

따라서 파싱이 필요하다. 다만 **인용부호가 전혀 없는 행**에서는 두 함정이 모두
성립하지 않으므로 바이트 경로가 정확하다 — 이것이 아래 빠른 경로의 근거다.

## 아키텍처

### 새 모듈: `src/convert.rs`

순수 로직(egui 없음). 이 코드베이스의 모듈 규율을 따른다 — `find.rs`, `edit.rs`,
`parse.rs`, `sort.rs`가 순수 로직이고 `app.rs`가 GUI다.

```rust
/// 한 행의 구분자를 `old`에서 `new`로 바꾼 문자열.
///
/// 인용부호가 없는 행은 바이트 경로(구분자 바이트만 교체)를 타고, 있으면
/// `split_fields` + `join_fields`로 폴백한다. 두 경로의 출력은 동일해야 한다.
pub fn convert_line(line: &str, old: u8, new: u8) -> String;

/// 문서 전체 변환. 실제로 **달라진** 행만 `(행번호, 새 텍스트)`로 돌려준다.
/// 인덱스 오름차순.
pub fn convert_all(lines: &[String], old: u8, new: u8) -> Vec<(usize, String)>;
```

### 빠른 경로와 폴백

`convert_line`의 판정:

1. 행에 `"`가 없으면(`memchr`) → **바이트 경로**: `old` 바이트를 `new`로 교체.
   단, 값에 `new`가 이미 있으면 인용이 필요하므로 이 경로를 쓸 수 없다. 즉
   **행에 `"`도 없고 `new` 바이트도 없을 때만** 바이트 경로.
2. 그 외 → `split_fields(line, old)` → `join_fields(fields, new)`.

이 규율은 Task G/H/I/M에서 확립한 것과 같다: **바이트 경로는 "확정" 아니면
"폴백"만 결론지을 수 있고, 절대 "아님"을 결론짓지 않는다.** 판정이 애매하면
폴백이 정답이다. 폴백은 느릴 뿐 틀리지 않는다.

**빠른 경로 조건이 완전한 근거.** `join_fields`가 인용을 씌우는 조건은 값에
`new` / `"` / `\n` / `\r`가 있을 때다. 조건 1이 `"`와 `new`를 이미 배제하고,
`\n`/`\r`는 **`EditBuffer.lines[i]`가 개행을 담지 않는다**는 이 코드베이스의
불변식이 배제한다. 따라서 조건 1을 통과한 행은 인용이 전혀 필요 없고, 구분자
바이트를 그대로 갈아 끼우는 것이 `split_fields`+`join_fields`와 같은 결과를
낸다.

실제 TSV/CSV의 대다수 행이 빠른 경로를 탄다.

### 병렬화

`rayon`의 `par_iter().enumerate().filter_map(...).collect()`. `sort.rs::sort_lines`와
`find::replace_all`이 쓰는 패턴과 같고, rayon의 `collect`가 인덱스 순서를
보존하므로 결정성이 유지된다.

### undo / dirty

`replace_all_in_doc`과 같은 규율:

- 실제로 **달라진 행만** undo에 담는다(같은 구분자를 고르면 애초에 `Convert`가
  비활성이지만, 인용 정규화로 인해 일부 행만 달라지는 경우가 있다)
- `EditOp::Replace` **하나**로 묶어 Ctrl+Z 한 번에 전체 복구
- 행 수는 변하지 않는다
- 변환 후 `doc.sep = SeparatorMode::Char(new)`로 맞춘다. 안 그러면 데이터는
  새 구분자인데 화면은 옛 구분자로 나누려 해서 표가 한 컬럼으로 무너진다
- 구분자가 바뀌므로 툴바가 하는 것과 같은 무효화를 한다: `sort`, `sort_job`,
  `selected_col`, `sort_specs`, `show_sort_dialog`, 그리고 `highlight`
  (컬럼 경계가 달라져 셀 단위 매치 위치가 무의미해진다)
- **`has_header`는 유지한다.** 변환은 필드 수도 행 수도 바꾸지 않으므로 헤더
  행은 그대로 헤더다. 이것을 지우면 0번 행이 데이터로 내려와 정렬·추출이
  헤더를 데이터처럼 다루게 된다

### 편집 모드 자동 진입

뷰 모드에서 `Convert`를 누르면 `enter_edit_mode(doc)`를 자동 호출한 뒤 변환한다.
Replace가 편집 전용이라 비활성화되는 것을 사용자가 불편해했으므로 같은 문제를
반복하지 않는다. 대용량 파일은 메모리를 많이 쓰므로 다이얼로그에 한 줄 안내를
둔다.

## UI

### 메뉴 항목

`Tools > Convert Delimiter…` — 기존 `Sort by Columns…`, `Row & Column Numbers…`
아래.

**텍스트 모드(`SeparatorMode::None`)면 비활성.** 나눌 기준이 없으므로 변환할
것도 없다.

### 다이얼로그

`egui::Window`. Sort / Numbering 다이얼로그와 같은 패턴.

```
┌─ Convert Delimiter ──────────────────────┐
│ Current delimiter:  Comma  ,             │
│                                          │
│ Convert to                               │
│   ○ Comma  ,        ○ Tab                │
│   ○ Pipe  |         ○ Semicolon  ;       │
│   ● Custom  [ ~ ]                        │
│                                          │
│ ⚠ 파일 내용이 바뀝니다. 되돌리려면        │
│   Ctrl+Z. 저장해야 디스크에 반영됩니다.    │
│                                          │
│                  [Cancel]  [Convert]     │
└──────────────────────────────────────────┘
```

`Convert` 버튼 비활성 조건:

- 고른 구분자가 현재 구분자와 같음 (no-op)
- Custom을 골랐는데 입력이 비었음
- Custom 입력이 **ASCII가 아님** (아래 참조)

### 커스텀 구분자는 ASCII만

`join_fields`가 `delim as char`로 비교하고 `out.push(delim_ch)`로 쓴다
(`parse.rs:298`). 비ASCII 바이트(예: `0xA9`)를 넘기면 `as char`가 U+00A9 `©`가
되어 UTF-8로 **두 바이트**가 쓰이는데, 파서는 한 바이트를 기대한다. 결과가
깨진다.

또한 툴바의 커스텀 입력은 `as_bytes().first()`로 **첫 바이트**를 취하므로
(`app.rs:985`), `£`를 입력하면 `0xC2`(UTF-8 선행 바이트)가 구분자가 된다.

따라서 이 다이얼로그의 커스텀 입력은 **ASCII 한 글자로 제한**하고, 아니면
`Convert`를 비활성화한다.

**기존 툴바의 같은 문제는 이 작업의 범위 밖이다** — 보기 전용이라 데이터를
깨뜨리지는 않는다. 별도 항목으로 남긴다.

## 정확성 계약

`convert_all`의 출력은 "각 행에 `split_fields` + `join_fields`를 적용한 것"과
**비트 단위로 같아야** 한다. 빠른 경로는 순수한 최적화이며 결과를 바꾸지
않는다.

### 테스트

- **차등 테스트 (전수 코퍼스)** — 알파벳 `{a, ", ,, \t, |}` 길이 0~4 전수에
  대해, `convert_line`과 참조 구현(`split_fields`+`join_fields`)이 정확히 같은
  문자열을 내는지. 구분자 쌍도 교차한다.
  Task I에서 랜덤 79.7만 건이 놓친 위음성을 따옴표 전수 프로브가 잡았으므로,
  랜덤이 아니라 전수로 한다.
- **빠른 경로 커버리지** — 위 코퍼스에서 빠른 경로를 탄 입력과 폴백을 탄 입력이
  **둘 다 0이 아닌지** 세어 확인한다. 이것이 없으면 빠른 경로가 통째로 죽어
  있어도(항상 폴백) 차등 테스트는 통과한다.
- **왕복** — `,`→`\t`→`,` 후 각 행의 **필드 값**(문자열이 아니라)이 원래와
  같은지. 인용이 늘 수 있으므로 문자열 동일성은 성립하지 않는다.
- **인용 안의 구분자 보존** — `홍길동,"서울, 강남구",30` → 탭 변환 시 필드가
  3개로 유지되는지.
- **새 인용 생성** — 탭 구분 `홍길동\t서울, 강남구` → 콤마 변환 시
  `홍길동,"서울, 강남구"`가 되는지.
- **undo 한 번에 전체 복구** — `EditOp::Replace` 하나로 묶였는지.
- **`doc.sep` 갱신** — 변환 후 새 구분자로 맞춰졌는지.
- **정렬/하이라이트 무효화** — 변환이 `sort`, `sort_specs`, `selected_col`,
  `highlight`를 지우는지.
- **no-op 미기록** — 실제로 달라진 행이 없으면 undo에 담기지 않고 dirty가 서지
  않는지.
- **버튼 비활성 규칙** — 순수 함수로 뽑아 테스트한다(아래 참조).

### 순수 함수 가드

`Convert` 버튼 비활성 판정은 egui 클로저 안에 인라인으로 쓰지 않고 자유 함수로
뽑아 프로덕션과 테스트가 **같은 함수**를 부른다.

```rust
fn convert_enabled(current: SeparatorMode, target: Option<u8>) -> bool;
```

이 코드베이스에서 반복적으로 나온 결함이다 — 테스트가 판정식을 복사해 인라인으로
적어 두면 진짜 가드를 지워도 테스트가 자기 사본만 보고 통과한다. 가드를 지우면
테스트가 **실패해야** 한다(변이 테스트로 확인).

## 성능

15.4M행 파일에서 `split_fields`는 행당 8개 String을 할당해 판정만으로 17.6초가
든다(Task M). 변환은 전 행이 대상이므로 그 비용을 피할 수 없어 보이지만:

- 인용부호 없는 행은 바이트 경로라 `split_fields`를 아예 부르지 않는다
- rayon 병렬화는 같은 파일에서 `replace_all`을 100~200ms대로 만들었다

목표: 실사용 파일(899MB, 15.4M행, TSV→CSV)에서 **1초 이내**.

## 범위 밖 (YAGNI)

- 구분자 자동 감지 변경 — 이미 열 때 감지한다
- 여러 문자 구분자 — 현재 자료구조가 `u8` 하나다
- 인코딩 동시 변환 — 인코딩 드롭다운이 따로 있다
- 뷰 모드에서 변환 — 편집 모드 자동 진입으로 해결
- 툴바 커스텀 입력의 비ASCII 문제 수정 — 보기 전용이라 데이터를 깨지 않는다.
  별도 항목
- 변환 전 미리보기 — Ctrl+Z가 있다
